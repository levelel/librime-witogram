# 阶段性调查报告：万象模型适配与 octagram / witogram 对比

## 1. 背景与目标

本阶段调查的目标，不是继续做零散的末端调分，而是先回答三个更基础的问题：

1. 当前万象词库与万象 grammar 模型，实际具有什么结构特征。
2. 为什么在使用同一套词库与 n-gram 模型的前提下，原版 `octagram` 能把目标句做对。
3. 为什么当前 `witogram + witset` 还做不对，以及这个失败究竟发生在哪一层。

本报告基于以下证据链整理：

- 本机万象词典与 grammar 工件检查。
- `RIME-LMDG` 公开 wiki / README / DeepWiki 的构建说明。
- `librime` 原版 `Syllabifier -> Dictionary -> Poet -> Grammar` 代码流。
- 当前 `witogram + witset` 的运行时代码与单句 probe / graph 工件。

---

## 2. 结论摘要

### 2.1 当前万象词库与万象 grammar 模型的关键特征

当前万象体系并不是“词典内容 = grammar token 集合”的一体化结构，而是明显分成两层：

1. **词典层**
   - 单字和多字词条都存在。
   - `zi.dict.yaml` 中明确存在 `一`，且包含多个读音与权重。
   - 句级词库中也存在 `第一站`、`一座`、`古老`、`小镇` 这类基础词块。

2. **grammar 模型层**
   - 当前 `wanxiang` 模型族的 `mini / big / lts` grammar 工件，都表现为**拆分 token 建模**。
   - 现成 `arpa` 与从 `.gram` 重新导出的结果都表明：
     - 有 `以`
     - 有 `已`
     - 有 `宜`
     - **没有 unigram `一`**
   - 因而 grammar 模型并不是词典条目的直接镜像，而是“分词后 n-gram 统计”的产物。

### 2.2 `一` 的缺失更像训练口径自然结果，而不是本地转换 bug

目前能确认：

- `RIME-LMDG` 的公开方法明确区分：
  - **单字频率统计**：不依赖分词，服务于单字词库。
  - **grammar 建模**：依赖分词结果、n-gram 统计和剪枝。
- 本地 `build_grammar.cc` 与 `GramDb::Build()` 只负责把上游 key/value 编码并构建 trie，不会单独过滤 `一`。
- 公开资料没有给出可核对的具体剪枝阈值，也没有证据表明存在“显式删除 `一`”的专门规则。

因此当前最稳妥的判断是：

- `一` 在词典层存在。
- `一` 在 grammar 模型层缺失。
- 这个缺口更像是**上游分词 + n-gram 统计 + 剪枝**的自然结果，而不是本地转换链路损坏。

### 2.3 `octagram` 能做对，不是因为它拥有更好的模型内容

原版 `octagram` 能做对，并不是因为它掌握了另一份更强的词库或另一份更强的 grammar 模型。

它真正占优的地方在于：

1. **上游 contract 更正确**
   - `Syllabifier` 会更早把 correction / completion / ambiguous joint 等风险写入 `credibility`。
   - `Dictionary` 会把这些 `credibility` 并入词条权重。
   - 因而句级搜索开始前，错误路径已经在上游先被压了一轮。

2. **句级 grammar 角色更薄**
   - `Poet` 做的是小 beam 的句级组合。
   - `octagram` 在句级只提供薄层的 collocation 调整。
   - 如果某个 token 没有更强搭配证据，原版更像是“没有额外奖励”，而不是“自动视为一条显式更差的 OOV 路径”。

3. **它更依赖已经存在的基础词块**
   - 当前词典里已有 `第一站`、`一座`、`古老`、`小镇`。
   - 原版并不需要靠 unigram `一` 独自翻盘。
   - 更合理的成功路径是：先保住 `第一站` 这条 family，再在句级把 `第一站 / 是 / 一座 / 古老 / 小镇` 组合起来。

### 2.4 当前 `witogram + witset` 的主问题不是“模型差”，而是“解释语义不匹配”

当前路线的主问题已经逐步收紧到：

1. **对当前万象 grammar 模型的解释语义不对**
   - `witogram` 中 `vocab.Index(word) == NotFound()` 会直接触发：
     - `used_char_fallback = true`
     - `oov_token_count > 0`
   - `witset_poet` 再把这些标记继续放大成额外惩罚。
   - 因而在当前实现里，“grammar 模型里没有 unigram `一`”会被解释成“这是一条显式更差的 fallback / OOV 路径”。

2. **句级搜索承担了过多补救责任**
   - `witset` 当前实现更像：
     - 先放大候选池
     - 再靠末端句级搜索和一组额外特征补救
   - 而原版 `octagram` 是：
     - 先用 `credibility` 在上游压掉坏路径
     - 再用小 beam 做句级组合

3. **当前模型的强项与当前实现的用法没有对齐**
   - 当前万象 grammar 更擅长拆分 token 路径上的局部搭配与上下文统计。
   - 但当前 `witogram + witset` 里，一旦某个表面词缺少 unigram 命中，就很容易被解释成整体 bad path。
   - 这把“缺少局部证据”误翻译成了“明确负证据”。

## 3. 万象词库与万象模型的结构特点

### 3.1 词典层的特点

从当前本机工件看，万象词典至少有三个特点：

1. **单字词典与句级词典都很全**
   - `一` 本身存在。
   - 句级常见基础块也存在，例如：
     - `第一站`
     - `一座`
     - `古老`
     - `小镇`

2. **同音近形词条丰富**
   - `yi* / shi*` 这类高歧义区会给 translator 产生大量可行路径。
   - 因而它天然需要较强的上游 contract 来防止错误 family 过早放大。

3. **词典是候选供给层，不等于 grammar 评分层**
   - 词典能给出候选，不代表 grammar 模型一定把它当作独立 token。

### 3.2 grammar 层的特点

当前万象 grammar 模型的关键特点是：

1. **更像拆分 token LM，而不是整词 LM**
   - 多字串通常不是一个独立 token。
   - 查询更像依赖 token 序列，而不是整词表面串。

2. **不存在“词典里有就一定能在 grammar 中整词命中”的保证**
   - `一` 这种单字，在词典中有，但在当前 grammar 模型中未作为 unigram 收录。

3. **当前 grammar 更适合被当作“局部上下文证据源”**
   - 它更像在回答：
     - 当前 token 序列在这个上下文里是否顺
   - 而不是在回答：
     - 这个表面词是不是一个强整词 token

### 3.3 这对算法提出的要求

如果继续使用当前万象词库 + 当前万象 grammar 模型，那么算法层必须适应以下事实：

1. **不能把 token 缺失简单等价成路径错误。**
2. **必须区分“缺少正证据”和“存在负证据”。**
3. **必须把更多风险判断前移到 translator / path contract，而不是全交给末端句级补救。**

## 4. 为什么原版 octagram 能工作

### 4.1 它的真正结构是“上游强、末端薄”

原版 `octagram` 的成功，不在于插件本身更复杂，而在于分层正确：

1. `Syllabifier`
   - 更早处理音节切分与 spelling 风险。
   - 将风险写入 `credibility`。

2. `Dictionary`
   - 将 `credibility` 纳入 `DictEntry.weight`。
   - 因而候选在进入句级阶段前，已经带有上游先验。

3. `Poet`
   - 使用较小 beam 做句级组合。
   - 不承担大规模候选救火职责。

4. `octagram`
   - 只提供薄层 grammar 搭配分。
   - 角色更像“句级调味”，不是“最后的主救火器”。

### 4.2 它没有把当前 grammar 的缺口放大成重惩罚

在原版语义里：

- 如果某个 token 没有获得更强搭配证据，通常只意味着：
  - 没有额外奖励
  - 或落到统一的 collocation penalty

它并不会自动把这种情况解释成：

- 明确的 OOV
- fallback 路径
- 需要继续被句级特征层层追加惩罚的坏路径

这恰好和当前万象 grammar 的性质更兼容。

### 4.3 它更早保住了正确 family

在 `第一站是一座古老的小镇` 这种 case 上，更合理的解释不是：

- 原版靠 unigram `一` 做对了句子

而是：

- 原版更早保住了 `第一站` 这条正确 family
- 没有把后续 `一座` 所在路径过早解释成显式坏路径
- 最终在句级上依靠已有基础词块组合出正确结果

## 5. 为什么当前 witogram + witset 不能工作

### 5.1 当前失败不是出在“没有候选”

当前大量 benchmark 与单句 probe 已经说明：

- 主要缺口不是候选召回。
- 主要缺口是排序与路径解释。

也就是说，问题不是“系统根本看不见正确答案”，而是：

- 正确路径在搜索和评分过程中被解释得太差。

### 5.2 当前失败首先出在 grammar 语义解释

当前 `witogram` 会把：

- `vocab.Index(word) == NotFound()`

直接翻译成：

- `used_char_fallback = true`
- `oov_token_count > 0`

而 `witset_poet` 会继续把它们转成额外惩罚。

这在当前万象 grammar 模型上会产生一个系统性偏差：

- **模型没有收录某个 unigram**
  - 在当前实现里，被解释成了“这是明显更差的路径”。
- 但从模型性质看，它更可能只意味着：
  - 模型没有以这个粒度提供证据。

### 5.3 当前失败还出在搜索形态

当前 `witset` 的整体形态，更像：

1. 先扩很宽的候选池。
2. 再用 `witset_poet` 和一组句级特征去补救。

这个形态的问题是：

- 错误 family 往往已经先放大了。
- 等到句级特征出手时，正确 family 已经错过最有利的剪枝时机。

之前多轮实验也支持这一点：

- 只调整末端特征强度，提升有限。
- 把 joint / edge / state 风险前移到搜索形态后，虽然提升仍小，但至少首次出现了正向信号。

### 5.4 当前失败还出在“模型假设”和“模型现实”错位

当前路线曾多次假设：

- 如果表面词是一个合理词块，那么 grammar 层应该能以相近粒度支持它。

但当前万象模型现实更像：

- grammar 是拆分 token 视角。
- 词典是表面词块供给层。
- 两者不是一一对齐的。

因此如果实现仍把“表面词 token 缺失”当作重负证据，就会持续错判。

---

## 6. 最终判断

### 6.1 主问题不是资源，而是契约

当前阶段最关键的判断是：

- `witogram + witset` 落后于原版 `octagram` 的主因，不是资源更差。
- 主因是：
  - **上游 contract 不够正确**
  - **grammar 语义解释不够适配当前万象模型**
  - **搜索形态仍偏向“先放大、后补救”**

### 6.2 当前最应该修的不是“更多末端特征”

如果目标是持平或超过原版 `octagram`，当前优先级不应是：

- 再加一个 `poet` 末端 patch
- 再试一个局部权重
- 再做一个表面 continuation bonus

而应是：

1. 修正 `witogram` 对当前 grammar 模型的解释语义。
2. 把歧义与 family/path contract 前移到 translator / request-stage / admission。
3. 让句级 `witset` 从“主救火器”退回到“强上下文组合器”。

### 6.3 这并不意味着 witogram 方向失败

恰恰相反，当前调查反而说明：

- `witogram` 的方向仍然有价值。
- 但它必须建立在**适配当前万象模型与万象词库现实形态**的前提上。

否则它的增强能力越强，反而越容易在错误语义上放大偏差。

---

## 7. 下一阶段建议

下一阶段不应继续做孤立 patch，而应进入“结构重对齐”：

1. **先修 grammar 解释语义**
   - 把“缺少 unigram 命中”从“重 OOV”改成“缺少局部正证据”。

2. **再修上游 contract**
   - 让 `translator` 更早保住 source-line / family。

3. **最后再让 witset 发挥强项**
   - 在候选池已更干净的前提下，用更强上下文表达超过原版 `octagram`。

- `适配万象模型的宏观方案：witogram + witset 持平或超过 octagram`
