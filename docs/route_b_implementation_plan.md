# Witogram 路线 B 实施方案

## 1. 文档目的

本文档用于明确 `witogram` 的最终目标、当前实现存在的关键问题、为什么选择“路线 B”，以及后续可执行的详细实施步骤。

这里的“路线 B”指的是：

- 不再把 `witogram` 仅仅视为 Rime 原生 `grammar` 插件的透明替代。
- 由 `witset` 自己的 `Poet` 接管句级评分逻辑。
- 将 `witogram` 退回为一个可复用的语言模型特征提供器。
- 在 `witset_poet` 中显式实现句级特征融合、校准、验证与回归体系。

这条路线的目标不是“尽量兼容旧实现的所有偶然行为”，而是把插件真正做成一个可解释、可验证、可持续优化的上位方案。

---

## 2. 最终目标

### 2.1 产品目标

`witogram` 的最终目标不是仅仅“能加载 `.klm`”，也不是“在少数句子上比 `octagram` 看起来更好”，而是：

1. 在长句、歧义句、同音高频冲突场景下，稳定优于原 `octagram`。
2. 保留 `KenLM + mmap` 在工程上的优势：
   - 更低的驻留内存占用
   - 更现代的二进制模型加载方式
   - 更好的可维护性和后续扩展性
3. 将“语言模型分数”从黑箱变成可解释的句级特征：
   - 能拆解每个候选为什么高分/低分
   - 能精确定位排序异常是由哪一项特征引起
4. 建立自动化验证体系，使后续改动不再依赖“手感调参”。

### 2.2 技术目标

路线 B 的技术目标是建立一个新的句级评分契约，而不是继续把所有问题都塞进 `Grammar::Evaluate()` 这一层。

最终希望实现的形态：

- `witogram` 负责：
  - 模型加载
  - 给定上下文和候选的句级/局部语言模型打分
  - 提供清晰的查询接口
- `witset_poet` 负责：
  - 收集候选路径
  - 计算多个显式特征
  - 做最终句级排序
  - 输出详细调试信息
- 自动化验证体系负责：
  - 离线评测
  - 回归对比
  - 指标汇总
  - 性能验证

## 3. 当前问题总结

当前代码虽然已经具备一定的工程基础，但从“真正优于 `octagram`”的标准看，仍存在结构性问题。

### 3.1 当前实现的问题不是单一 bug，而是契约失配

当前链路大致如下：

1. `dump_to_arpa` 将原 `.gram` 转成 `.arpa`
2. `build_binary` 将 `.arpa` 转成 `.klm`
3. `witogram::Query()` 返回 KenLM 分数
4. `witset_poet` 将 `entry->weight` 与 `grammar_->Query()` 进行再融合

问题在于，这四层之间没有一个被严格定义、严格验证的统一契约。

结果表现为：

- 分数可以产生，但排序并不稳定
- 局部看似合理，整体却不如 `octagram`
- `grammar/weight` 的调整缺乏稳定意义
- 某些句子中高频单字组合会压过更合理的上下文词序列

### 3.2 当前 `.klm` 不是严格等价的标准语言模型

当前 `dump_to_arpa` 做了大量启发式处理，例如：

- 对原值做缩放与全局平移
- 缺失 prefix 人工补默认值
- 缺失 1-gram 人工补默认值
- backoff 使用统一常量

这意味着目前生成的 `.klm` 更像“兼容性近似模型”，而不是严格还原自原始 `.gram` 的标准 KenLM 概率模型。

这会导致两个后果：

1. 语言模型分数本身可能不稳定。
2. 后续再与 Rime 字典权重叠加时，量纲更难对齐。

### 3.3 当前 `witset_poet` 的融合方式不是严格的对数线性模型

目前 `witset_poet` 的融合逻辑本质上仍然是“启发式混分”。

这和真正意义上的 log-linear model 有明显差异：

- 特征没有被显式定义
- 特征尺度没有被系统校准
- 权重不是通过数据驱动搜索得到
- 长度偏置、OOV 惩罚、词边界偏好没有被独立建模

因此，README 中“更科学的对数线性模型”这一宣称，在现阶段并不稳固。

### 3.4 继续沿用 Rime 原生 grammar 契约，会限制上限

Rime 原生 `Grammar::Evaluate()` 的设计目标，是做一个轻量级的附加语言模型加分器。

它适合：

- 简单上下文加权
- 和字典权重直接相加

它不适合：

- 多特征句级融合
- 独立建模 OOV / 边界 / 长度
- 可解释调试输出
- 明确的句级特征校准

如果继续强行在这个契约里做“上位替代”，上限会非常低。

## 4. 为什么选择路线 B

### 4.1 路线 A 的问题

路线 A 的核心思想是尽量保留 Rime 原生契约，只把 `witogram` 做成一个更强的 `grammar` 插件。

这条路线的好处是改动小，但问题在于：

1. 评分权力仍然掌握在旧契约手里。
2. 难以引入多特征句级融合。
3. 很难把“比 `octagram` 更优”做成一个可证明、可验证的结果。
4. 继续依赖“混分微调”，容易陷入长期拉扯。

### 4.2 路线 B 的优势

路线 B 虽然改动更大，但它真正释放了 `KenLM` 和自定义 `Poet` 的能力。

它的核心优势：

1. **明确职责分层**
   - `witogram` 只负责语言模型查询
   - `witset_poet` 负责句级融合
2. **特征可解释**
   - 每个候选分数可以拆开看
3. **更适合自动化验证**
   - 可以离线做指标评测与回归
4. **更适合长期演化**
   - 未来可以自然引入用户词典特征、边界特征、语义特征
5. **更符合“上位替代”的目标**
   - 不再只是“兼容原接口”
   - 而是真正设计一套更好的评分体系

### 4.3 为什么路线 B 更有资格支撑 README 中的宣传

如果要继续保留这些宣传方向：

- 更科学的评分体系
- 更优于 `octagram`
- 更适合大型模型与长期迭代

那么路线 B 是唯一真正有希望把这些话做实的路径。

路线 A 最多能做到工程层面的改进，而路线 B 才能把“模型优势 + 排序优势”落到可验证的结果上。

## 5. 路线 B 的最终设计原则

### 5.1 核心原则

1. **句级排序必须由 `witset_poet` 主导**
2. **`witogram` 只输出明确定义的 LM 特征**
3. **每个特征都必须可解释、可打印、可单测**
4. **所有重要改动必须通过自动化回归验证**
5. **先建立稳定契约，再考虑训练新模型**
6. **拼音歧义消解与句级排序视为一体能力**

### 5.2 关于“拼音歧义是否应单独惩罚”的阶段性判断

结合本轮调研与基线结果，当前更合理的设计理念是：

- 不把拼音歧义路径视为“特殊坏候选”并在进入句级排序前直接判死刑；
- 不再把“是否来自歧义切分”当作一票否决条件；
- 而是把由歧义切分产生的候选，与其他普通候选一起放入统一候选集合；
- 最终由 `witset_poet` 的句级特征融合在完整上下文中决定谁胜出。

这样做的理由有三点：

1. 从产品视角看，用户只关心最终输出对不对，并不关心错误究竟发生在“拼音切分”还是“句级排序”哪一层。
2. 从系统视角看，连写全拼输入本来就会诱发音节边界歧义；如果把这部分能力人为剥离，评测将无法覆盖真实输入场景。
3. 从工程视角看，`Rime` 原生 syllabifier 已经对 `die = di + e`、`qian = qi + an` 这类歧义关节施加过 `credibility` 惩罚；路线 B 不应再简单叠加“硬惩罚”，而应把这类路径作为普通候选交给统一句级排序处理。

需要强调的是：

- “不把歧义路径单独判死刑”不等于“完全忽略结构差异”；
- 更合理的做法是引入统一的、可解释的句级结构特征；
- 这些特征不直接看“你是不是歧义路径”，而是看“你在完整句子里是否形成了更紧凑、更连贯、更像自然语言的结构”。

### 5.3 基于这一原则的新算法草案

推荐将路线 B 的句级评分进一步升级为“统一歧义候选排序”模型：

```text
final_score
= a * dict_score_norm
+ b * lm_total_logprob
+ c * lm_avg_logprob
+ d * merge_gain
+ e * path_compactness
+ f * context_consistency
+ g * length_term
+ h * user_bonus
```

其中新增三类关键特征：

- `merge_gain`
  - 对每个候选词同时计算整词路径与逐字路径的 LM 分数差；
  - 若整词解释明显优于逐字解释，则得到更高分；
  - 它不是“歧义惩罚”，而是“哪种解释在当前上下文里更自然”的直接证据。
- `path_compactness`
  - 衡量整条句子路径是否出现明显的“长词 + 单字尾巴”“异常碎片化”结构；
  - 例如 `皇帝 + 俄`、`牵起 + 按` 这类路径会自然较差；
  - 该特征对所有候选统一生效，而不是只针对歧义切分。
- `context_consistency`
  - 衡量候选在完整前文中是否与局部语义、句法边界、常见搭配保持一致；
  - 它本质上是把“是否像一句自然中文”显式建模，而不是依赖单一词频或单一 LM 总分。

推荐的执行策略：

1. 上游 `syllable graph` 允许保留歧义路径；
2. `witset_poet` 扩大句级保留宽度，避免正确路径在早期被剪掉；
3. 不再单独为“歧义路径”追加一刀切惩罚；
4. 改为让 `merge_gain / path_compactness / context_consistency` 在统一句级排序中自然压制坏路径。

### 5.4 可行性评估

这个方向是可行的，而且与路线 B 高度一致。

现阶段已经具备的基础：

1. `witogram` 已经能够输出：
   - 总分
   - 平均分
   - 整词路径分数
   - 逐字路径分数
2. `witset_poet` 已经接管句级排序，并能输出详细调试分项；
3. 自动化基线脚本已经能稳定跑 `300` 条语料并生成回归报告。

因此，后续实现新算法所需的主要工作不是“推倒重来”，而是：

1. 在 `witset_poet` 中增加统一结构特征；
2. 调整候选保留宽度，减少正确路径在句级排序前被裁掉；
3. 用自动化基线持续验证这些特征是否真的压住了 `di'e / qi'an` 一类错误路径。

预计难点主要有两项：

1. 候选数会继续增大，必须谨慎控制全局裁剪策略；
2. 结构特征如果设计过于激进，可能会误伤真实短词或口语表达。

总体判断：

- 该设计方向合理；
- 与“拼音歧义消解和排序能力应综合考虑”的目标一致；
- 可以作为路线 B 后续阶段的基本设计理念之一。

### 5.5 推荐的句级评分公式

推荐将最终句级评分显式定义为：

```text
final_score
= a * dict_score_norm
+ b * lm_avg_logprob
+ c * boundary_score
+ d * oov_penalty
+ e * length_term
+ f * user_bonus
```

其中：

- `dict_score_norm`
  - Rime 字典权重的归一化版本
- `lm_avg_logprob`
  - 候选句的平均语言模型对数概率
- `boundary_score`
  - 词边界/切分偏好特征
- `oov_penalty`
  - 未登录词/未知 token 惩罚
- `length_term`
  - 长度修正项，用于控制句长偏置
- `user_bonus`
  - 用户词典或自学习加成

初期可以只实现前四项，后续再扩展。

### 5.6 为什么强调“平均 logprob”

如果直接累加整句总分，长句天然更吃亏，长度偏置会非常明显。

因此建议优先使用：

- 平均 token logprob
- 或做简单长度归一化后的总分

这样能让 LM 特征在不同句长之间更可比。

## 6. 实施方案总览

路线 B 建议分为四个阶段推进。

### 阶段 0：冻结当前错误认识，建立基线

目标：

- 不再继续“拍脑袋调权重”
- 固化一批回归样例
- 明确当前版本的真实表现

交付物：

- 回归样例集
- 当前排序结果快照
- 当前耗时/内存快照

### 阶段 1：重构评分契约与调试输出

目标：

- 将 `witset_poet` 中的评分拆成显式特征
- 每个候选输出分项日志
- 建立离线验证脚本

交付物：

- 新版句级评分结构
- JSON/日志形式的详细打分明细
- 可重复运行的离线评测脚本

### 阶段 2：重做转换链路

目标：

- 审查并重构 `dump_to_arpa`
- 弱化当前启发式补丁对最终排序的污染
- 重新生成对比模型

交付物：

- 新版转换脚本
- 新版 `.arpa/.klm`
- 与旧版本对比报告

### 阶段 3：训练自己的标准 KenLM

目标：

- 彻底摆脱“旧 `.gram` 兼容转换”的历史包袱
- 构建真正适合 `witogram` 的标准语言模型

交付物：

- 字级或字词混合的标准 KenLM
- 训练脚本与语料处理脚本
- 新模型评测报告

### 阶段 4：稳定化与发布

目标：

- 建立日常回归流程
- 固化调参方式
- 更新 README 和对外表述

交付物：

- 自动化回归脚本
- 文档
- 最终发布说明

## 7. 详细实施步骤

## 7.1 阶段 0：建立基线

### 目标

在开始改造前，必须先回答三个问题：

1. 当前版本到底在哪些句子上排序错误？
2. 错误是由 `entry->weight` 主导，还是由 LM 分数主导？
3. 当前版本的耗时、候选数、内存占用是多少？

### 具体工作

1. 建立样例集：
   - 高频同音干扰
   - 长句上下文依赖
   - 标点与前文影响
   - 原 `octagram` 强项场景
2. 固化当前排序结果：
   - 候选列表
   - Base 分数
   - 最终显示顺序
3. 记录性能基线：
   - 首条候选耗时
   - 全候选生成耗时
   - RSS

### 预计工作量

- 1 到 2 天

---

## 7.2 阶段 1：重构 `witset_poet` 评分契约

### 目标

让每个候选的最终得分都可分解、可解释。

### 具体工作

1. 将当前混分代码拆成显式特征项：
   - `dict_score_raw`
   - `dict_score_norm`
   - `lm_score_raw`
   - `lm_score_norm`
   - `oov_penalty`
   - `boundary_score`
   - `length_term`
   - `final_score`
2. 修改日志输出格式，保证每个候选都能打印上述分项。
3. 引入句级分数结构体，避免后续继续用临时变量拼凑。
4. 暂时保留现有模型，只验证新契约和日志链路。

### 验收标准

1. 给定任意候选，能完整打印全部分项。
2. 能明确回答某个错误排序是由哪项分数主导。
3. 日志足够稳定，可供脚本解析。

### 预计工作量

- 2 到 4 天

---

## 7.3 阶段 1.5：建立自动化验证体系

### 目标

把“是否更好”从主观感受变成可量化结果。

### 自动化验证内容

#### 1. 样例级回归测试

输入固定测试句，输出：

- 候选列表
- 各候选分项分数
- Top-1 / Top-3 是否命中预期

#### 2. 候选排序指标

对一批样例统计：

- Top-1 Accuracy
- Top-3 Accuracy
- MRR
- Pairwise Correctness

#### 3. 对抗样例集

专门覆盖：

- 身后 / 神后
- 身旁 / 神旁
- 高频单字误压合理词组
- 长句中局部歧义

#### 4. 性能测试

自动统计：

- 平均耗时
- P95 / P99
- RSS

### 建议产出文件

- `metrics.json`
- `ranking_dump.json`
- `regression_report.md`

### 预计工作量

- 2 到 3 天

---

## 7.4 阶段 2：重做转换链路

### 目标

减少当前 `.gram -> .arpa -> .klm` 过程中启发式补丁导致的语义失真。

### 当前转换链路的主要问题

1. 原始值处理方式不保证标准条件概率语义
2. prefix 与 1-gram 的补洞方式过于粗糙
3. backoff 为统一常量，缺乏真实上下文依赖

### 具体工作

1. 审查原 `.gram` 值语义：
   - 它到底表示什么分数
   - 是否可以恢复局部条件关系
2. 重写转换策略：
   - 尽量按 prefix 建模而不是全局平移
   - 明确缺失项的补齐规则
3. 生成多份对照模型：
   - 旧转换版
   - 新转换版
   - 可选的弱回退版/强回退版
4. 跑自动化指标对比

### 验收标准

1. 转换脚本逻辑可解释
2. 新模型在样例集上优于旧模型
3. 不再需要通过拍脑袋调 `weight` 才能勉强工作

### 预计工作量

- 5 到 10 天

---

## 7.5 阶段 3：训练自己的标准 KenLM

### 是否一定要训练

短期不是必须，但长期大概率需要。

原因：

- 当前旧 `.gram` 转换链路很难真正支撑“标准概率分布”的宣传
- 如果要把 `witogram` 做成真正上位方案，最好拥有属于自己的标准训练流程

### 建议的第一版训练方案

先训练一版字级 KenLM：

1. 收集中文语料

## 10. 与 Witset / OutwitSettingsServer 的联动边界

路线 B 虽然主要聚焦于 `witogram` 与 `witset_poet` 的句级评分体系，但 `witset` 并不是孤立插件，它还与 `OutwitSettingsServer` 的本地 PPL、Prefill、Beam Search 与后续重排序能力保持联动。

因此，后续推进必须把“联动边界”视为硬约束，而不是实现细节。

### 10.1 当前已确认的联动链路

当前链路可以概括为：

1. `WitsetTranslator` 生成句候选，并将上下文信息写入 Rime Context。
2. `WitsetPoet` 负责本地候选路径构建、基础排序与 Prefill 触发时机。
3. `WitsetProcessor` 在按键触发后，按当前 `llm_level` 选择：
   - 本地 PPL 重排序
   - LLM 驱动的 Beam Search
4. `ppl_client_cpp` 通过命名管道把请求发往 `OutwitSettingsServer`。
5. `OutwitSettingsServer` 负责：
   - 本地 PPL 批处理
   - 相关缓存与健康状态维护
6. 结果返回后，Rime 侧通过 `SentenceCache` 写回候选并刷新 UI。

### 10.2 后续改造时不能破坏的部分

路线 B 早期阶段改造 `witset_poet` 时，以下能力不能被破坏：

1. **`llm_level_2` 的 PPL 请求时机**
   - 不能因为本地打分拆分而改变当前分号触发纠错与请求的行为。
2. **`SentenceCache` 的候选与 PPL 回写结构**
   - 现有 PPL 结果回写与 UI 刷新链路必须保持兼容。
3. **Prefill 触发条件**
   - `effective_prefix` 的截断、去重与异步预填充时机不能随意改坏。
4. **不重新引入 Warmup 旁路**
   - 目前 `warmup` 路线已经被放弃，不能因为本地评分调整再次恢复额外的预热请求与调度分支。
5. **命名管道协议与 FBS 输入输出结构**
   - 第一阶段不应修改 `witset` 与 `OutwitSettingsServer` 的通信协议。

### 10.3 第一阶段允许改动的范围

在不影响上面边界的前提下，第一阶段可以安全推进的内容主要包括：

1. 将 `witset_poet` 的本地候选分数拆成显式分项；
2. 增强调试输出，使每个候选的基础分数来源可解释；
3. 建立可供离线脚本解析的日志或导出格式；
4. 在不改变外部协议的前提下，为后续验证体系提供更稳定的数据基础。

### 10.4 第一阶段明确不做的事

为避免误伤联动链路，第一阶段明确不做以下事情：

1. 不改 `OutwitSettingsServer` 的请求协议；
2. 不改 `ppl_client_cpp` 的数据结构；
3. 不改 `SentenceCache` 的外部契约；
4. 不改变 PPL / Beam Search 的触发条件；
5. 不改变 `llm_level` 的行为分层。

### 10.5 为什么必须先写入计划文档

如果不把这条边界提前写清楚，后续很容易出现一种典型误区：

- 为了优化本地句级排序，顺手改动了与 `OutwitSettingsServer` 联动的请求时机或数据结构；
- 最终导致本地排序变化和服务端重排序变化混在一起，无法判断是哪一层出了问题。

因此，路线 B 的正确推进方式是：

- 先稳定联动边界；
- 再做本地评分体系重构；
- 最后才考虑是否需要同步调整服务端协作方式。

## 14. 阶段性成果报告（截至当前 300 条基线）

### 14.1 本轮阶段目标

本轮工作的目标不是继续停留在“能跑通快照链路”，而是：

1. 将 `witogram` 从单一 `Query()` 分值扩展为更丰富的 LM 特征提供器；
2. 将 `witset_poet` 从旧的启发式混分，升级为显式句级特征融合；
3. 用真实 `300` 条基线验证这一轮底层替换是否真的带来准确度提升。

### 14.2 当前已经完成的改造

本轮已完成的关键改造包括：

1. `witogram` 新增更细粒度的 LM 特征输出：
   - `total_log10`
   - `avg_log10`
   - `whole_word_log10`
   - `char_path_log10`
   - `char_path_avg_log10`
2. `witset_poet` 已从简单的 `Dict + LmScaled` 叠加，升级为显式分项融合；
3. 自动化基线脚本已能对 `300` 条样本产生：
   - `metrics.json`
   - `baseline_run_metadata.json`
   - `regression_report.md`
4. 已建立“改动前基线备份 -> 改动后重跑 -> 指标对比”的基本流程。

### 14.3 本轮基线结果

在 `300` 条截断基线上，当前版本相较于本轮改造前的备份结果，已经出现明显提升：

- `Top-1 Accuracy`: `0.358804 -> 0.534884`
- `Top-3 Accuracy`: `0.435216 -> 0.661130`
- `total_records`: `7037`
- `expected_not_found_count`: `83`

这说明：

1. 路线 B 的底层替换方向是有效的；
2. 当前改造不是“换了一套更复杂但无收益的系统”；
3. `witogram + witset_poet` 已经具备继续向 `octagram` 水平逼近的现实基础。

### 14.4 本轮暴露出的剩余问题

当前结果虽然明显优于上一个版本，但还暴露出三类结构性问题：

1. **高频错词仍可能压过正确表达**
   - 例如 `心事` 被 `新式`、`医械` 一类高频错词压制。
2. **OOV 或近 OOV 区的区分力不足**
   - 例如 `一眼 / 一验 / 一研 / 一演` 一类尾字几乎打平。
3. **拼音歧义切分产生的坏路径仍能活到最终候选**
   - 例如 `黄蝶 -> 皇帝俄`
   - `轻轻浅浅 -> 轻轻牵起按`

### 14.5 本轮最重要的新认识

本轮调研后，关于“拼音歧义与排序”的认识发生了关键变化：

1. 这不应再被视为两个割裂的问题；
2. 真正要超过 `octagram`，就必须把“歧义切分 + 句级排序”视为统一能力；
3. 因此，后续算法不应试图把歧义候选完全挡在门外，而应把它们纳入统一句级排序中解决。

这个认识将直接影响下一阶段的特征设计与基线评估方式。

## 15. `Rime + octagram` 对照基准测试方案

### 15.1 为什么必须建立 `octagram` 对照基线

路线 B 的最终目标不是“比旧版 `witogram` 更好”，而是：

- 在真实输入场景下，匹配或超过原版 `octagram` 的效果。

因此，必须建立一条可重复运行的 `Rime + octagram` 对照基线。

### 15.2 当前结论：现有基线脚本不能直接原样用于原版小狼毫

当前 `witogram` 基线脚本不能直接原样打到你安装的原版小狼毫上，原因包括：

1. 当前脚本依赖我们自己编译的 `rime_api_console.exe`；
2. 脚本依赖额外控制命令，例如：
   - `set preceding text`
   - `clear composition`
3. 当前评测链路依赖 `witset_translator` 自己导出的本地快照 JSONL；
4. 原版小狼毫目录中没有现成的 `rime_api_console.exe` 可直接复用。

换句话说：

- **评测逻辑可以复用**
- **驱动层不能直接复用**

### 15.3 对你当前机器环境的阶段性判断

当前本机环境里：

- `C:\Program Files\Rime\weasel-0.17.4` 中可以看到标准 `rime.dll` 和内置 schema；
- 这些 schema 确实保留了“使用八股文语言模型”的 patch 钩子；
- 但目前没有在安装目录或用户目录中直接看到 `octagram` 命名的插件文件、模型文件或专门配置；
- 因此，不能仅凭“安装了原版小狼毫”就断定当前环境已经真正启用了 `octagram`。

### 15.4 推荐的对照测试方法

推荐把对照基线分成两个层次：

#### A. 评测框架复用

保留当前基线脚本的高层逻辑：

1. 读取同一份测试语料；
2. 生成同一份参考答案；
3. 统计同一套指标：
   - `Top-1`
   - `Top-3`
   - `MRR`
   - 错例报告

#### B. 驱动层替换

不要继续使用 `rime_api_console.exe`，改为使用一个新的“原版 Rime 驱动器”：

1. 直接加载：
   - `C:\Program Files\Rime\weasel-0.17.4\rime.dll`
2. 使用：
   - `shared_data_dir = C:\Program Files\Rime\weasel-0.17.4\data`
   - `user_data_dir = C:\Users\Bing\AppData\Roaming\Rime`
3. 通过 `ctypes` 或一个小型 C++ 驱动调用 Rime API：
   - 创建 session
   - 选择 schema
   - 注入按键
   - 拉取候选列表

这意味着：

- 现有脚本可以作为“评测框架”保留；
- 但必须新增一个“stock Rime backend adapter”；
- 当前已经存在的 `test/rime_interaction.py` 可以作为这个驱动器的基础原型。

### 15.5 是否应直接复用当前安装的小狼毫

结论是：

- **如果只是验证“当前原版小狼毫环境下的表现”**，可以尝试直接复用；
- **如果要得到可信、可复现、可与 `witogram` 正面对比的 `octagram` 基线**，更推荐单独建立隔离环境。

原因：

1. 当前用户目录里混有大量其他 schema、脚本和自定义配置；
2. 无法确认当前是否真正加载了 `octagram`；
3. 若直接在日常使用环境里改动配置，容易把基准测试和日常输入环境混在一起。

### 15.6 推荐的最终方案

推荐建立一个单独的 `octagram benchmark` 环境：

1. 保持 `weasel-0.17.4` 的标准 `rime.dll` 不变；
2. 新建一个独立的用户目录，例如：
   - `C:\Users\Bing\AppData\Roaming\Rime_octagram_bench`
3. 在该目录中复制与 `witty` 当前测试环境一致的关键输入变量，而不是做“最小环境”裁剪：
   - `dicts/sentence`
   - `grammar`
   - `zhuma.sentence.dict.yaml`
   - `shuangpin_algebra.yaml`
4. 建立一个专用 bench schema，使其：
   - 使用原版 `script_translator + poet/octagram`
   - 词库指向 `zhuma.sentence`
   - `grammar.language` 指向同一份 `grammar/wanxiang-lts-zh-hans`
   - `speller.algebra` 复用同一份 `shuangpin_algebra`
5. 用专门的 benchmark driver 对这个目录跑同一份语料。

### 15.7 是否需要重新编译 `librime-octagram`

当前阶段的判断是：

- **很可能需要。**

理由：

1. 目前无法从你现有安装目录中确认 `octagram` 插件已真实存在且启用；
2. 即使原版小狼毫保留了 `grammar` patch 钩子，也不等于本机当前环境已具备可测的 `octagram` 运行链路；
3. 若要得到可信对照组，最稳妥的方法仍然是：
   - 获取 `librime-octagram`
   - 针对与 `weasel-0.17.4` 匹配的 `librime` 版本编译插件
   - 部署到隔离 benchmark 环境中

### 15.8 推荐执行顺序

推荐的执行顺序如下：

1. 先验证当前原版小狼毫环境是否真的启用了 `octagram`；
2. 如果确认未启用，建立隔离 benchmark 目录；
3. 编译并部署与当前 `weasel-0.17.4` 匹配的 `librime-octagram`；
4. 实现新的 stock Rime benchmark driver；
5. 用同一份语料分别跑：
   - `witogram + witset_poet`
   - `stock Rime + octagram`
6. 输出统一对比报告。

当前进展：

- 独立 bench 用户目录 `C:\Users\Bing\AppData\Roaming\Rime_octagram_bench` 已建立；
- 与 `witty` 对齐的 `dicts/sentence`、`grammar`、`zhuma.sentence.dict.yaml`、`shuangpin_algebra.yaml` 已复制；

### 15.9 这条方案的可行性评估

这条方案是可行的，但比当前 `witogram` 自测链路更复杂。

主要工作量在于：

1. 搭一个不依赖 `rime_api_console.exe` 的驱动层；
2. 准确确认并部署 `octagram`；
3. 维护一套与 `witty` 关键变量一致的隔离原版 Rime 基准环境。

但从路线 B 的目标看，这项工作是值得的，因为：

- 没有 `octagram` 对照基线，就无法真正回答“现在到底离原方案还有多远”。

  - `expected_not_found_count = 83`

### 16.3 这组数字说明了什么

这组数字给出一个非常关键的判断：

1. 当前版本输给原版，且差距不小。
2. 当前版本的主要弱点不是“候选根本出不来”，而是“候选已经出来了，但最终排错了”。
3. 从 `expected_not_found_count` 看，当前 `witogram` 的候选存在性并不比原版更差，甚至略少于原版的缺失量。
4. 因此，当前最该攻克的是统一句级排序能力，尤其是歧义拼音诱发的碎裂路径排序。

### 16.4 必须承认的阶段性结论

必须明确承认：原版 `octagram` 对歧义拼音路径的处理虽然粗暴，但在当前真实语料上是有效的。

它有效，不是因为它“理论上更优雅”，而是因为它在真实输入里稳定完成了下面这件事：

- 让 `di'e / qi'an` 一类碎裂切分更难进入最终头部候选；
- 让 `皇帝 + 俄`、`牵起 + 按` 这种结构不紧凑的路径更早掉队；
- 在句级排序还不够强时，用一条简单但稳定的规则先保住了整体正确率。

这意味着路线 B 后续不能再假设“只要把歧义路径放进统一候选集合，正确答案自然会赢”。

统一排序这个方向本身没有错，但必须补上真正能压制碎裂路径的强证据特征，否则只是把坏路径公平地保送到最后一轮。

## 17. 为什么当前实现还赢不过它

结合当前代码，最核心的结构性缺口有三点：

1. `witogram::ScoreFeatures()` 已经同时算出了：
   - `whole_word_log10`
   - `char_path_log10`
   - `char_path_avg_log10`
   - `matched_whole_word`
2. 但 `witset_poet` 目前只把这些证据弱化成了：
   - 一个固定的 `whole_word_bonus`
   - 一个固定的 `char_fallback_penalty`
   - 再叠加通用的 `boundary / length / oov`
3. 也就是说，系统还没有显式利用“整词解释比逐字解释到底好多少”这个最关键的信息。

这会导致两个直接后果：

- 明明是 `整词解释显著更自然` 的路径，目前只多拿到一个很小的常数奖励；
- 明明是 `碎裂解释必须靠 char_path 才勉强成立` 的路径，目前也只是被轻微惩罚，而不是被句级证据系统性压低。

换句话说，当前实现还没有把“歧义抑制”升级为“基于语言模型证据的歧义判别”。

## 18. 下一步算法：证据化歧义抑制

### 18.1 基本判断

下一步不应直接照抄原版 `octagram` 的硬惩罚，也不应继续坚持“完全不额外抑制歧义路径”。

更好的做法是：

- 保留统一候选池；
- 不对“来自歧义切分”做先验一票否决；
- 但在句级排序里显式加入能反映“碎裂路径不自然”的强证据特征。

### 18.2 推荐新增的三个主特征

#### A. `merge_gain`

定义：

```text
merge_gain = whole_word_logprob - char_path_logprob
```

解释：

- 如果某个候选作为整词解释时明显优于逐字解释，说明“合并成一个更完整的词”更符合语言模型；
- 这正是压制 `身后 -> 神后`、`黄蝶 -> 皇帝俄` 这类错误路径所需要的核心证据；
- 它比“是否歧义路径”更细，因为它只在整词解释真正更优时才发力。

#### B. `fragment_penalty`

目标：

- 显式惩罚“长词 + 单字尾巴”“异常碎词链”“整句碎裂度过高”的路径。

典型坏结构包括：

- `皇帝 + 俄`
- `牵起 + 按`
- 一个句子里连续堆出多个单字词来拼出看似完整的结果

这个特征不看音节图来源，只看最终句子结构，因此仍然符合“统一排序”的路线。

#### C. `ambiguity_margin`

目标：

- 不是问“这条路径是不是歧义产生的”，而是问“它是否只能依赖弱解释才存活”。

可实现为：

- 当候选没有可靠整词匹配、且 `char_path` 质量显著差于同位置其他候选时，额外扣分；
- 当候选整词命中且 `merge_gain` 为正时，给出更强的句级优势。

### 18.3 为什么这套方法有机会胜过原版

原版 `octagram` 的优势在于简单、稳定、保守。

而这套方法要胜过它，依赖的是三点：

1. **更精准**
   - 不把所有歧义路径一刀切打死，只打击那些“整词证据弱、碎裂证据强”的坏路径。
2. **更句级**
   - 不只看单个词，而是看整条句子是否呈现异常碎片化。
3. **更可解释**
   - 每个候选都能打印：
     - `merge_gain`
     - `fragment_penalty`
     - `ambiguity_margin`
   - 后续调参和回归会比原版“黑箱惩罚”更可控。

### 18.4 当前实现这一步的切入点

当前代码已经具备实现这一步的大部分基础：

1. `witogram` 已能同时给出整词路径和逐字路径分数；
2. `witset_poet` 已经有显式分项结构和调试导出；
3. 离线基线脚本已经能稳定对 `300` 条语料做回归。

因此，下一步最合理的切入顺序是：

1. 在 `witset_poet` 中新增 `merge_gain`；
2. 再新增句子级 `fragment_penalty`；
3. 最后再根据同位置候选差异加入 `ambiguity_margin`；
4. 每做完一项，都继续与当前保存的 `octagram_300_20260516` 对照。

### 18.5 这一阶段的成功标准

这一阶段不要求立刻全面超过原版，但至少要出现下面的可验证变化：

1. `di'e / qi'an` 类错误路径在头部候选中的出现率显著下降；
2. `Top-1 Accuracy` 明显向原版 `0.683333` 收敛；
3. `expected_not_found_count` 不明显恶化；
4. 错例报告中，“候选明明存在但被碎裂路径压过”的比例下降。

### 18.6 事后复盘：这一组“证据化歧义抑制”并未发展成主线

本节最初提出的 `merge_gain / fragment_penalty / ambiguity_margin` 思路，本质上仍然属于：

- 在 `witset_poet` 句级末端追加更强证据项；
- 试图用更精细的后验打分，把已经进入候选池的坏路径压回去。

后续实际推进结果表明，这条思路只验证出两点：

1. **它的分析方向部分正确**
   - 当前错误确实常常与：
     - 整词解释 vs 碎裂解释的可比性失衡；
     - `LM` 账本在不同切分 regime 下的系统性不可比；
     - 以及局部 continuation 强弱失衡
     有关。
2. **但它的实现落点偏晚**
   - 单靠在 `poet` 末端继续补特征，无法稳定复现原版 `octagram` 的任务结构优势；
   - 真正需要前移的，是候选进入 `poet` 之前的可信度契约，而不是再增加新的末端证据项。

因此，本节可保留为“为什么后段证据化抑制在理论上看起来合理”的历史记录，但不再作为当前优先实现入口。

## 19. 下一阶段四种候选方案

### 19.1 命名说明

为避免与本文前面“路线 A / 路线 B”的历史命名冲突，本节单独使用“方案 A / B / C / D”来指代下一阶段准备逐个验证的四条技术路线。

这里的四种方案，不是在否定本文主线“由 `witset` 主导排序”的目标，而是在回答一个更具体的问题：

- 当当前 `witset_poet` 的句级后罚已经显示出明显天花板后；
- 下一步到底应该把“歧义抑制”放在什么层级；
- 应该先试哪一种，才能最快验证哪条路最值得继续投入。

### 19.2 方案 A：前移为路径原始权重

核心思想：

- 不再把歧义抑制主要放在 `witset_poet` 末端追加 `penalty_score`；
- 而是把 `witset` 关心的歧义信号，前移为更早期的路径权重；
- 让这些信号像原版 `octagram` 的 `credibility` 一样，尽早进入 `entry->weight` 或与之等价的上游分数。

它要解决的问题是：

- 当前 `Octa` 虽然比 `Tail` 更有效，但仍然只是“句级阶段的事后补罚”；
- 真正的问题不是“罚得不够狠”，而是“坏路径进入句级排序时已经太晚”。

推荐的最小实现方向：

1. 找到 `witset` 当前能稳定观测到的歧义来源：
   - spelling overlap
   - ambiguous joint
   - 某位置是否只能靠异常碎裂扩展继续存活
2. 将这些信号汇总成一个轻量的 `path_prior` 或等价字段；
3. 在进入 `MakeSentences()` 前，直接体现在候选边或 `DictEntry` 的基础权重里；
4. 让 `witset_poet` 只做句级精排，而不是承担主要纠偏职责。

优点：

- 最接近原版有效机制；
- 有机会同时提高准确率与剪枝效率；
- 一旦成立，会比继续堆后罚特征更稳定。

风险：

- 会触碰比 `witset_poet` 更早的链路；
- 如果信号定义不稳，可能污染所有候选的基础权重；
- 需要非常谨慎地区分“歧义切分低可信”与“正常短词路径”。

### 19.3 方案 B：joint-aware beam state

核心思想：

- 不直接把歧义做成最终句子的惩罚项；
- 而是在 beam 搜索状态里显式携带“这条路径经过了什么类型的可疑 joint”；
- 让搜索过程本身具备歧义感知能力。

与当前做法的区别：

- 当前是候选句子已经形成后，再根据“长词后连续单字补尾巴”等结构现象扣分；
- 方案 B 是在扩展每一条 beam 时，就知道这条路径是否来自低可信切分，并把它作为状态的一部分参与比较和剪枝。

推荐引入的状态字段：

- `joint_penalty_acc`
- `ambiguous_joint_count`
- `recent_joint_type`
- `recent_fragment_run`
- `path_compactness_hint`

推荐比较方式：

1. `base_score` 仍然保留 `dict + lm` 主导；
2. 新增一组很轻的状态先验，只在候选分数接近时拉开顺序；
3. 在支配关系判断中，把“主分数接近但 joint 风险更低”的路径优先保留；
4. 不把这些字段直接暴露成重惩罚常数，先把它们当作 beam 内部排序和 prune 的辅助信号。

优点：

- 对原版 `Rime` 主链路侵入最小；
- 基本仍可把改动限制在 `witset` 自己的搜索状态与比较逻辑内；
- 很适合作为第一条试验路线，先验证“更早感知歧义”是否已经能明显优于末端后罚。

风险：

- 如果只改 beam 比较、不改上游边权，收益可能有限；
- 需要小心状态维度膨胀，否则会进一步放大一档性能压力；
- 若支配规则设计不当，可能把真正正确但早期看起来“有风险”的路径过早剪掉。

### 19.4 方案 C：联合词图与音节图的一次性路径求解

这是四个方案里最激进、但从算法形态上也最完整的一条路线。

核心思想：

- 不再先生成大量词候选，再交给 `witset_poet` 做末端句级补救；
- 改为把“音节切分可信度 + 词典路径权重 + 语言模型得分 + 结构约束”统一到同一张图上；
- 最终通过一次 DP / Viterbi / beam-Viterbi 混合求解，直接找整条最优路径。

它要替代的不是某一个特征，而是当前这整个流程：

1. 先让上游把大量可能路径都放进来；
2. 再在 `witset_poet` 里用很多后验特征努力把坏路径压回去。

方案 C 的基本图模型可以这样理解：

- 节点：
  - 输入串位置 `pos`
  - 必要时再加局部 LM 状态 `lm_state`
  - 可选地再加“最近 joint 风险状态”
- 边：
  - 一条边代表从 `pos_i -> pos_j` 的一种解释
  - 这条解释同时包含：
    - 一段 spelling / syllable 切分
    - 一条词典候选或单字候选
    - 该边自身的可信度与局部代价
- 路径：
  - 一条完整路径直接对应一个候选句
  - 目标不再是“收集许多句子后再排序”，而是“在图上直接求分数最高的句子路径”

推荐的第一版评分拆解：

```text
path_score
= dict_edge_score
+ syllable_joint_score
+ lm_transition_score
+ boundary_score
+ compactness_score
+ optional_user_bonus
```

其中每一项的含义应明确分层：

- `dict_edge_score`
  - 词典项本身的基础权重
- `syllable_joint_score`
  - 切分经过 ambiguous joint 时的可信度代价
- `lm_transition_score`
  - 由 `witogram` 基于前缀状态给出的局部语言模型增量分
- `boundary_score`
  - 词边界合理性与长度归一化
- `compactness_score`
  - 只在必要时对明显碎裂路径做轻量结构校正

推荐的实现步骤不是一步重写，而是分成四层原型：

1. **原型 C0：图导出与离线求解**
   - 不改线上排序；
   - 先把某些输入的音节图、词边、边分数导出为离线文件；
   - 写一个离线 DP/Viterbi 求解器，验证这种统一图求解是否能在坏例上优于当前 `witset_poet`。

2. **原型 C1：固定小状态 DP**
   - 只带 `pos + 最近 N 个 token 的 LM state`；
   - 不引入复杂的多样性策略；
   - 目标是先验证纯图搜索结果是否已经优于现有“生成后排序”。

3. **原型 C2：beam-Viterbi 混合**
   - 在每个 `pos` 上只保留有限个最优状态；
   - 把当前 `sentence_beam_size` 风格的宽搜索，收缩为“每个位置的有限状态最优保留”；
   - 这样复杂度更可控。

4. **原型 C3：替换 `witset_poet` 主路径**
   - 当 C1/C2 的离线指标已经明显更好时；
   - 再考虑让线上主路径从“候选池 + 句级排序”切到“联合图求解”。

方案 C 为什么可能最强：

1. 它把当前最割裂的三件事统一了：
   - 切分
   - 词典路径
   - 句级语言模型
2. 它不再依赖“后面再救回来”的假设；
3. 它天然更符合“正确路径应在搜索过程中逐步领先”的直觉。

方案 C 的主要工程难点：

1. `lm_state` 的表示与缓存需要设计清楚；
2. 图状态一旦过大，复杂度会很快失控；
3. 必须先有离线可视化和可验证原型，否则容易在重写过程中失去对照基线；
4. 需要谨慎处理 Rime 现有候选、多样性和 UI 期望的兼容边界。

我对方案 C 的具体建议是：

- 不要一上来在线上替换；
- 先把它当作一个“离线求解器实验框架”；
- 只挑最典型的歧义长句回放；
- 只要离线结果已经明显优于当前 `witset_poet`，再决定是否把它工程化。

### 19.5 方案 D：让模型本身提供更强分词证据

核心思想：

- 不把主要赌注压在人工规则、路径先验或图搜索结构上；
- 而是让模型本身对“整词是否比碎字更自然”提供更强证据。

可选方向：

1. 训练真正的词级 KenLM；
2. 训练字词混合 KenLM；
3. 为高频词块单独构造更稳定的 token 体系；
4. 重新定义 `witogram` 查询接口，使其天然支持词块与字级混合对比。

优点：

- 从根本上补强“模型证据不足”的问题；
- 长期最有利于摆脱当前兼容转换链路的历史包袱。

风险：

- 周期最长；
- 若搜索契约本身仍不合理，单纯换模型未必能解决排序失败；
- 训练、清洗、回归的工程成本都较高。

### 19.6 推荐试验顺序

结合当前代码结构、对原版机制的理解，以及改动风险，推荐按以下顺序逐个尝试：

1. **先试方案 B**
   - 原因：侵入最小，最适合作为“比句级后罚更早一步，但仍不碰上游 Rime 主链”的第一轮验证。
2. **再试方案 A**
   - 原因：若 B 证明“前移歧义信号”方向有效，就继续把它推到更早的路径原始权重层。
3. **然后做方案 C 的离线原型**
   - 原因：它最可能带来形态级提升，但工程跨度最大，必须建立在前两轮对信号定义更清楚的前提下。
4. **方案 D 放在长期**
   - 原因：更像模型代际升级，不适合作为当前这一轮“先把搜索契约做对”的首选。

### 19.7 当前阶段的明确判断

基于本轮 `Tail` 与 `Octa` 的结果，当前最应避免的是：

- 继续在 `witset_poet` 里堆更多同类句级后罚项；
- 希望通过再调几个常数，就把 `Top-1` 从当前水平直接推近原版 `octagram`。

当前更可靠的策略应当是：

- 先验证“歧义信号更早进入搜索过程”是否有效；
- 再决定是否值得投入更大规模的联合图求解重构。

### 19.8 阶段性反省：当前方向哪里对，哪里不对

经过方案 `B -> A -> C` 的连续对照后，目前应把“是否继续投入”拆成两个问题来看：

1. `witogram + witset` 这个总方向是否仍值得做；
2. 当前这条“先放大候选池，再靠 `witset_poet` 末端补救”的实现路线是否仍值得继续深挖。

当前判断是：

- 第一问没有被证伪；
- 第二问已经表现出明显天花板。

#### 19.8.1 为什么原版 `octagram` 能用更粗糙的方法做出更好的效果

关键不是它的句级特征更复杂，而是它在**更早、更正确的层级**干预了搜索空间。

原版 `octagram` 的强项不是：

- 在 `poet` 末端做更精细的整句排序；

而是：

- 在 syllable graph / query / dictionary weight 这条链路上，通过 `credibility` 很早就把 ambiguous joint 压低；
- 让很多坏路径在进入句级阶段前就已经不具备竞争力。

这会直接带来两个结果：

1. beam 可以更窄，但头部候选更干净；
2. 句级搜索承担的是“比较少数合理路径”，而不是“从大量脏路径里事后救火”。

因此，原版看起来“粗糙”，本质上却是在搜索契约上更高效。

#### 19.8.2 当前路线真正的理论优势是什么

当前路线的真正理论优势，不是单纯“更平滑”，而是：

1. **句级上下文表达能力更强**
   - 有机会利用更长上下文，修正局部合理但全句不自然的路径。
2. **统一建模能力更强**
   - 可以把词典、边界、结构、局部歧义、LM 增量统一纳入同一套路径分数。
3. **后续扩展空间更大**
   - 若搜索契约正确，后续无论接更强 LM、混合词字模型还是更多句级特征，都更容易纳入。

所以它的优势不是“更优雅”本身，而是：

- 理论上它有机会在保留上游约束的同时，进一步利用句级证据超越原版。

#### 19.8.3 为什么这些优势目前还没有兑现

因为当前实现把最重要的职责放错了位置。

现阶段已经反复验证到：

- 方案 B：把歧义信号放进 beam 状态，信号真实进入链路，但 `Top-1` 不动；
- 方案 A：把同一份信号前移进主分数，`Top-1` 仍不动；
- 方案 C：一旦开始改变搜索形态，就第一次出现正向信号；
- 但继续往状态里塞局部 edge 风险后，先带来了状态分裂和性能回升，准确率仍没继续前进。

这说明：

- 当前瓶颈不是“特征不够多”；
- 而是搜索契约仍然在假设“先放进来，再靠末端排序救回来”。

#### 19.8.4 目前是否还值得继续投入

只靠“理论上更强”这个理由，已经不值得继续在当前路线下大规模投入。

但如果问题改成：

- 能否换一种正确的搜索契约，既保留 `witogram` 的句级表达能力，又像原版 `octagram` 一样在更早层级约束搜索空间；

那么答案仍然是：

- 值得继续，但必须换实现方向。

#### 19.8.5 当前最稳的阶段性结论

目前应当明确接受以下判断：

1. 继续在 `witset_poet` 里叠加更多后验特征、更多状态桶、更多常数，不应再被当作主线。
2. 当前这条末端补救路线，不应再预期最终自然超过原版。
3. 若还要继续追平甚至超过原版，必须依赖新的搜索契约，而不是旧契约上的继续打补丁。

### 19.9 下一步主线：更换为正确的搜索契约

这里所谓“更换为正确的契约”，不是简单再加一个新特征，而是把系统的职责重新分层：

- 上游负责尽早表达切分可信度与路径先验；
- 中游负责在有限状态空间内保留真正有希望的路径；
- 下游只负责少量合理路径之间的句级比较，而不是大规模救火。

#### 19.9.1 新契约的目标

新的主线目标应改写为：

1. **不要先放大再补救**
   - 搜索过程本身就应逐步淘汰低可信路径。
2. **让正确路径更早领先**
   - 不是依赖最终候选池里“再排序”才翻盘。
3. **让句级 LM 承担精排职责，而不是承担主清洗职责**
   - `witogram` 的全局表达能力应服务于“精排”，不是替代前半段搜索约束。

#### 19.9.2 推荐的新实现顺序

后续不再按“加更多状态维度”的思路推进，而按下面顺序推进：

1. **阶段 N1：先做 edge 风险降噪**
   - 只保留真正高价值的局部风险信号。
   - 初步建议：
     - 优先保留 `ambiguous` 与强负 `credibility`
     - 暂时移除或弱化 `abbreviation / completion / fuzzy`
     - 对单字、短跨度 edge 设更严格门槛
   - 目标：
     - 验证当前 edge 风险之所以无收益，是否主要是噪声过多。

2. **阶段 N2：做离线 C0 图求解器**
   - 不先改线上主路径；
   - 将典型坏例导出为音节图 + 词边 + 局部代价；
   - 写一个离线 DP / Viterbi 求解器，直接验证“正确契约”在坏例上的排序是否优于当前 `witset_poet`。
   - 目标：
     - 用最小成本确认“统一图求解”是否真有价值。

3. **阶段 N3：把线上 `WitsetPoet` 压缩为有限状态保留器**
   - 不是再扩状态桶；
   - 而是明确引入“每个 `pos + state` 只保留最佳路径”的契约，并逐步贴近离线求解器的状态定义。
   - 目标：
     - 让线上主路径与离线正确契约逐步对齐。

4. **阶段 N4：决定是否替换现有主路径**
   - 只有当离线 C0/C1 的结果已经稳定优于当前线上版时，才考虑替换。

#### 19.9.3 下一步最直接的执行项

如果继续开发，最直接、最不绕弯的下一步应是：

1. 为 edge 风险定义做一次明确降噪；
2. 再跑 `300` 条基线，判断“edge 风险进入状态但无收益”是否主要是噪声问题；
3. 同时开始准备离线 C0 所需的数据导出接口。

#### 19.9.4 N2 首轮结果：离线 C0 已出现正信号

在完成 `edge` 风险降噪后，已经进入 `N2` 的第一轮最小实现：

1. 在真实 `WitsetTranslator::Query()` 链路中新增 `graph.jsonl` 导出；
2. 复用现有 `rime_api_console.exe` + `run_local_snapshot_baseline.py` 路径生成与 `reference_cases` 对齐的图快照；
3. 新增一个最小离线 `DP / Viterbi` 求解脚本，先只用：
   - 词边 `DictEntry.weight`
   - 顶点风险 `vertex_risk`
   - edge 风险 `edge_risk`
   - 单字惩罚 / 多字轻奖励

第一轮结果已经给出一个重要信号：

- 同一批 `300` 条 `reference_cases` 上
- 当前线上一档 `witset` 指标仍为：
  - `Top-1 = 0.541528`
  - `Top-3 = 0.684385`
- 而最小离线 `C0` 指标已达到：
  - `Top-1 = 0.600000`
  - `Top-3 = 0.750000`

这说明：

- 即使还没有把 `LM` 增量、全句上下文和更复杂的状态带进来；
- 仅靠“统一图上的路径求解”这一契约变化，本身就已经优于当前线上框架。

因此，`N2` 已经不再只是概念预研，而是得到了**首个客观正向证据**。

在此之后，又做了两步校验性推进：

1. **数据审计**
   - 独立重算后确认：
     - `Top-1 = 180 / 300 = 0.600000`
     - `Top-3 = 225 / 300 = 0.750000`
   - 并已在离线 solver summary 中显式输出：
     - `top1_hit_count`
     - `top3_hit_count`
     - 各匹配口径计数

2. **C0.1 小状态验证**
   - 第一版 `C0.1` 同时引入了：
     - 小状态保留
     - 额外状态打分
   - 结果回落到：
     - `Top-1 = 176 / 300 = 0.586667`
     - `Top-3 = 220 / 300 = 0.733333`
   - 随后做了变量隔离版 `C0.1 state_only`
     - 只保留状态，不改变原始局部打分
     - 结果与 `C0` 完全一致：
       - `Top-1 = 180 / 300 = 0.600000`
       - `Top-3 = 225 / 300 = 0.750000`

这说明：

- `C0` 的提升不是统计口径误差；
- 但“只要加入少量结构状态，结果就会继续自然上升”这一假设，目前没有得到支持；
- 下一步不应继续围绕更多结构状态桶打转，而应转向为离线 `C0` 引入**更有信息量的局部证据**。

#### 19.9.5 当前不再作为主线的方向

从现在开始，以下方向不再应被当作主线：

- 继续增加新的句级后罚项；
- 继续堆叠更多近似状态桶，希望自然把 `Top-1` 推上去；
- 继续把主要赌注压在“末端排序器会自己纠正前面放进来的坏路径”这个假设上。

#### 19.9.6 `c0_ctx` 当前卡点的真实根因

在继续推进转移级 `LM/context` 证据后，最新一次 `c0_ctx` 的直接结果一度显示：

- `evaluated_case_count = 96`
- `missing_graph_case_count = 204`

如果只看这组数字，很容易误判为：

- `c0_ctx` 的匹配键设计有严重问题；
- 或 `transition_lm_features` 基本没有导出成功。

但继续做工件级核对后，当前更可靠的结论是：

- 这次 `96/300` 的主因不是算法，而是**baseline 工件来自不同 run**
- 具体表现为：
  - `witset_local_snapshot.jsonl` / `witset_local_snapshot.graph.jsonl` 的修改时间更新到了较新的 partial rerun
  - 但 `snapshot_summary/reference_cases.jsonl` 与 `baseline_run_metadata.json` 仍停留在更早一轮完整 run
- 于是 `run_c0_graph_solver.py` 实际上是在拿：
  - 一份新的 partial `graph/snapshot`
  - 去匹配一份旧的 `300-case reference`

因此：

- 当前这组 `96/300` **不能用于判断 `c0_ctx` 路线成败**
- 它只说明：当前验证流程允许工件错配，而不是 `c0_ctx` 已被证伪

#### 19.9.7 已做的流程修复

为了避免后续继续在错配工件上浪费时间，已经补了两处工具链保护：

1. `run_local_snapshot_baseline.py`
   - 不再只在整轮成功结束后才写 `reference_cases.jsonl` 与 `baseline_run_metadata.json`
   - 现在会在运行开始时先落空文件，并在每个 text step 后持续刷新
   - 若中断退出，metadata 会留下 `status = interrupted`

2. `run_c0_graph_solver.py`
   - summary 新增：
     - `graph_record_count`
     - `reference_case_count`
     - `coverage_ratio`
     - `graph/reference` 文件时间戳与大小
     - `warnings`
   - 当出现“低覆盖 + graph/reference 新旧错位”时，会直接显式报警

这意味着后续再出现类似问题时，solver 不会再给出一个表面正常、但实际上建立在错配工件上的结果。

#### 19.9.8 下一步约束

因此，`c0_ctx` 的下一步不应是继续调权重，而应遵守如下顺序：

1. 先拿到**同一轮 run** 生成的完整 `reference + snapshot + graph`；
2. 确认 `coverage_ratio` 恢复到接近 `1.0`；
3. 再去判断转移级 `LM/context` 证据是否真的修复：
   - `街口 / 接口`
   - `沙沙 / 啥啥`
   - 以及其他“骨架已对，但最终词选错”的案例。

#### 19.9.9 完整同轮工件上的最终复核结果

上述约束已经全部执行完毕：

- baseline 已重新完整跑通：
  - `completed_text_steps = 300`
  - `status = completed`
- `c0_ctx` 的覆盖也已恢复正常：
  - `evaluated_case_count = 300`
  - `missing_graph_case_count = 0`
  - `coverage_ratio = 1.0`
  - `warnings = []`

这说明此前的 `96/300` 确实只是工件错配，不是 `c0_ctx` 的固有覆盖问题。

#### 19.9.10 完整 graph 下的规模修复

拿到完整 graph 后，又暴露出另一条真实约束：

- 完整 `witset_local_snapshot.graph.jsonl` 已膨胀到约 `103.65 GB`
- 原版 `run_c0_graph_solver.py` 会先 `load_jsonl(graph_path)` 整文件入内存
- 在完整 graph 上会直接触发 `MemoryError`

因此工具链又补了一步必要修复：

- 不再整文件加载 graph
- 改为：
  1. 先读取小的 `reference_cases.jsonl`
  2. 提取本轮会评估的 `input` 集合
  3. 流式扫描 `graph.jsonl`
  4. 只保留这些目标 `input` 对应的索引记录

这一步修复的是“验证工具能否处理真实完整工件”，不改变 `c0/c0_ctx` 的评分契约。

#### 19.9.11 同轮对照结果

在同一轮、完整对齐工件上：

- 当前线上 baseline：
  - `Top-1 = 0.541528`
  - `Top-3 = 0.684385`
- `c0`：
  - `Top-1 = 180 / 300 = 0.600000`
  - `Top-3 = 225 / 300 = 0.750000`
- `c0_ctx`：
  - `Top-1 = 169 / 300 = 0.563333`
  - `Top-3 = 212 / 300 = 0.706667`

因此，完整验证后可确认：

- `c0` 的正信号依旧成立
- `c0_ctx` 虽然数值上仍高于当前线上 baseline，但**明显劣于纯 `c0`**

#### 19.9.12 `c0_ctx` 相对 `c0` 的错例性质

进一步逐例对比 `c0` 与 `c0_ctx`：

- `both_correct = 169`
- `fixed_by_ctx_vs_c0 = 0`
- `regressed_by_ctx_vs_c0 = 11`
- `both_wrong = 120`

也就是说：

- 当前 `c0_ctx` **没有修好任何一条** 原本 `c0` 没修好的 case
- 却额外把 `11` 条本来已经被 `c0` 选对的 case 弄错了

典型回退并不是“结构更合理，只是答案不同”，而是明显的局部字词级退化，例如：

- `那个 -> 哪个`
- `映照 -> 应照`
- `体验到了 -> 体验到乐`
- `风景中 -> 风景得`
- `证件等 -> 证件登`

这说明当前把转移级 `LM/context` 证据**逐 edge 直接累加**的用法，会破坏 `c0` 已经选对的短语完整性与整句骨架。

#### 19.9.13 路线更新

因此，当前最合理的路线更新是：

- 不再把“继续调 `ctx_* weight`”当作主线
- 真实上下文证据不是完全没价值，但它当前更适合作为：
  - `c0` 末端少量候选之间的 tie-break / rerank 信号
  - 或“骨架已固定”之后的局部同音词判别证据
- 而不适合作为整张图、每一步转移都直接累计的主打分项

换言之，`c0` 当前已经证明“正确契约”本身成立；而 `c0_ctx` 则证明“把真实 context 证据直接前移到逐边打分”这条具体用法目前是有害的。

#### 19.9.14 `c0_ctx_rerank` 最小原型结果

为了验证“问题是不是只在于 `ctx` 用得太早”，又补了一个更保守的最小原型：

- `c0_ctx_rerank`
  - 先用纯 `c0` 生成末端候选路径
  - 只对接近最佳 `base score` 的末端路径补一个缩放后的 context rerank bonus
  - 当前实验参数：
    - `ctx_rerank_scale = 0.15`
    - `ctx_rerank_margin = 12.0`

在完整同轮工件上的结果：

- `Top-1 = 168 / 300 = 0.560000`
- `Top-3 = 212 / 300 = 0.706667`

对照关系：

- 线上 baseline：`0.541528 / 0.684385`
- `c0_ctx`：`0.563333 / 0.706667`
- `c0_ctx_rerank`：`0.560000 / 0.706667`
- `c0`：`0.600000 / 0.750000`

逐例对比：

- 相对 `c0`
  - `fixed = 0`
  - `regressed = 12`
- 相对 `c0_ctx`
  - `fixed = 1`
  - `regressed = 2`

因此，`c0_ctx_rerank` 的结论同样已经足够清楚：

- 即使把 `context` 降级到末端 rerank，只要仍沿用当前这套 path-level context 累积分定义，也没有带来净收益
- 这说明问题不只是“用在太前面”，还包括：
  - 当前 `context` 分数定义本身会偏好局部字词替换
  - 它缺少“仅在同骨架近邻候选之间生效”的更强约束

#### 19.9.15 下一步应进一步收窄的契约

因此，若还要继续验证 `context` 的真实价值，更合适的下一步不应是：

- 继续调 `ctx_* weight`
- 继续在 `c0_ctx` / `c0_ctx_rerank` 这种整路径 context 累积分上打转

而应收窄为更局部的实验契约：

1. 先固定 `c0` 已经选出的整句骨架；
2. 只在同起止边、同长度模式、或同骨架近邻候选之间做局部替换；
3. 只让 `context` 参与这些局部同音词决策；
4. 不再允许 `context` 对整条路径进行重新洗牌。

#### 19.9.16 错句复查后的进一步确认

按“不要只看 2% 左右的统计差异，而要看实际错句”的原则，对 `c0_ctx` 与 `c0_ctx_rerank` 又做了逐例复查。

复查结论是：

- 相对 `c0` 的回退并不主要是“另一种也合理”的轻微波动
- 大量是明显错误的局部替换或坏切分，例如：
  - `而 -> 二`
  - `店里 -> 电力`
  - `体验到了 -> 体验倒了`
  - `度过了 -> 读过了`
  - `等 -> 登`
  - `的 -> 德`
  - `却 -> 确`

因此，`c0_ctx` / `c0_ctx_rerank` 相对 `c0` 的负收益，更像稳定偏差，而不只是统计噪声。

#### 19.9.17 `c0_ctx_local` 最小原型

基于这个判断，又进一步实现了更窄的局部原型：

- `c0_ctx_local`
  - 先固定 `c0` 已选出的路径骨架
  - 不允许整条路径重排
  - 只在每个已选 edge 上比较：
    - 同 `start/end`
    - 同字数
    - 的近邻候选
  - `context` 只影响“当前词 + 下一词”的局部转移

当前实验参数：

- `ctx_local_scale = 0.10`
- `ctx_local_base_margin = 2.5`
- `ctx_local_gain_threshold = 0.30`

完整同轮工件上的结果：

- `Top-1 = 169 / 300 = 0.563333`
- `Top-3 = 213 / 300 = 0.710000`

对照关系：

- 线上 baseline：`0.541528 / 0.684385`
- `c0_ctx`：`0.563333 / 0.706667`
- `c0_ctx_rerank`：`0.560000 / 0.706667`
- `c0_ctx_local`：`0.563333 / 0.710000`
- `c0`：`0.600000 / 0.750000`

#### 19.9.18 `c0_ctx_local` 的错句性质

逐例对比：

- 相对 `c0`
  - `fixed = 0`
  - `regressed = 11`
- 相对 `c0_ctx`
  - `fixed = 4`
  - `regressed = 4`
- 相对 `c0_ctx_rerank`
  - `fixed = 4`
  - `regressed = 3`

它确实比整路径 rerank 更“收敛”，也能修回一部分明显的 `ctx` 型局部错字：

- `应照 -> 映照`
- `争去 -> 争取`
- `方家 -> 放假`
- `确 -> 却`

但它仍会引入新的明显坏替换：

- `店里 -> 电力`
- `度过 -> 读过`
- `是 -> 事`
- `而 -> 二`

因此当前最可靠的结论进一步收敛为：

- `context` 信号并非完全无价值
- 但即使收窄到局部 edge 替换，只要缺少更强的候选约束，它仍不足以形成净收益

#### 19.9.19 `c0_ctx_local_top1` 的边界结论

为了把“固定 `c0` 骨架”贯彻到底，又继续实现了更严格的版本：

- `c0_ctx_local_top1`
  - 只允许在 `c0` 的 `top-1` 骨架上做局部替换
  - 不允许低分骨架带着局部替换翻盘
  - 只接受 `base` 不变差的候选（`alt_base >= chosen_base`）

完整同轮工件上的结果：

- `Top-1 = 180 / 300 = 0.600000`
- `Top-3 = 212 / 300 = 0.706667`

与 `c0` 的逐例对比结果非常关键：

- `fixed = 0`
- `regressed = 0`
- `changed_top1_text_count = 0`

也就是说：

- `c0_ctx_local_top1` 的 `Top-1` 与纯 `c0` **逐例完全一致**
- 一旦真正固定 `c0` 的 `top-1` 骨架，并禁止低分骨架靠 context 信号翻盘，当前这套 `transition LM/context` 逻辑对 `Top-1` 既**没有增益，也没有伤害**

这一步把路线边界说明得更清楚了：

1. 之前那些明显坏句，核心根因确实是：
   - 允许低分骨架或低 `base` 候选被 context 翻盘；
2. 但在真正阻断这一点后：
   - 当前 `context` 信号又不足以把 `c0` 的 `Top-1` 再往上推。

因此，当前主线可以进一步收敛为：

- 若目标是继续提升 `Top-1`，继续在当前 `transition_lm_features` 上做局部替换 / 局部 rerank，收益空间已经基本见底；
- 当前最有价值的收获，是明确了这组 context 信号的能力边界，而不是找到了新的稳定增益项。

#### 19.9.20 `c0` 剩余错例的第一轮分型

在确认 `context` 支线收益见顶后，主线已切回 `c0` 本身。

对 `c0` 剩余 `120` 条错例，先按最可计算、最不主观的口径做第一轮程序化分型：

1. `top3_hit` 但 `top1` 未中：
   - 直接视为明显的 `base` 错排；
2. `top3` 未中，但 graph 中存在精确期望路径：
   - 视为更深层的 `base` 错排；
3. graph 中不存在精确期望路径：
   - 视为候选/图生成问题。

分型结果非常集中：

- 总错例数：`120`
- `top3_hit = 45`
- `exact_path_below_top3 = 74`
- `no_exact_path = 1`

也就是说：

- `119 / 120` 的错例，图里都存在精确期望路径；
- 真正的“图里没有正确路”只剩 `1` 条。

#### 19.9.21 唯一的真缺路径个案

当前唯一确认的上游候选缺失个案是：

- `case_000262`
- `input = kanshizai`
- 期望：`看似在`

对应 graph 中的候选只有：

- `看时 / 看市 / 看事`

- `是在 / 实在 / 石在 ...`

没有 `似`，也没有 `看似`，因此这条可以明确归为上游候选缺失，而不是 `c0` 排序失误。

#### 19.9.22 剩余 119 条的错句性质

对另外 `119` 条“路径存在但没选中”的错例，再看错句与期望之间的编辑距离：

- `top3_hit = 45`
  - 距离 `1`：`27`

这说明当前 `c0` 的剩余主问题并不是：

- 大量正确骨架根本没出来；
- 或 graph 大面积缺失正确路径。

更像是：

- 正确路径已经在图里；
- 很多错句只差 `1~4` 个字；
- 但 `dict/base` 分数仍把错误近音词、错误短语或错误词边压到了前面。

#### 19.9.23 主线更新

因此，当前最值得继续的主线不再是补 `context`，而是继续拆 `c0` 本体的错排来源：

1. 为什么精确期望路径已经存在，却上不去 `Top-3` / `Top-1`；
2. 哪些是局部近音词权重错误；
3. 哪些是多词组合总分偏差；
4. 哪些是单字/碎词路径仍被抬得过高。

#### 19.9.24 `c0` 剩余错例的第二层细分

为了避免“base 错排”这个结论过于笼统，又对这 `119` 条“路径存在但没选中”的错例继续做了第二层细分。

方法是：

- 先在 graph 上重建每条 case 的“最佳精确期望路径”；
- 再把它与 `c0` 当前 `top1` 的分词边界和局部词位进行对照；
- 用启发式把错例继续分成：
  - `local_homophone`
    - 分词边界基本一致
    - 但 1~2 个局部词位被近音词压错；
  - `combination_bias`
    - 不只是局部 1~2 词替换
    - 更像多词组合整体总分偏差；
  - `fragment_elevated`
    - 相比精确期望路径，`top1` 有明显更多的切分段或更多单字。

当前结果：

- `local_homophone = 51`
- `combination_bias = 68`
- `fragment_elevated = 0`

也就是说，在当前 `c0` 剩余错例里，真正的主问题已经明显收敛到前两类，而不是“碎词路径广泛过高”。

#### 19.9.25 代表性例子

`local_homophone` 代表例：

- `街口 -> 接口`
- `沙沙 -> 啥啥`
- `微凉 -> 微量`
- `中学时的 -> 中学是的`
- `肩头 -> 箭头`

`combination_bias` 代表例：

- `我抬头看那一树树的枝桠 -> 我抬头看哪艺术输得质押`
- `回到西安的街道 -> 回到闲的街道`
- `阳光从叶隙间漏下来 -> 阳光从业席间漏下来`

#### 19.9.26 关于“碎词/单字抬高”的当前地位

这条支线需要特别澄清：

- 在更早的 C 路线里，“碎词/单字路径抬高”确实是一个重要问题；
- 但在当前 `c0` 的剩余错例里，它已经不是主导矛盾。

目前只发现 `2` 条出现“`top1` 的单字数多于精确期望路径”的局部例外：

- `轻轻覆在往事之上 -> 轻轻负载往实质上`
- `国际工人代表大会上 -> 国际公认代表大会上`

因此，当前主线应更明确地聚焦在：

1. 局部近音词的 `base` 权重错排；
2. 多词短语组合的总分偏差；

而不应继续把主要精力放在“碎词路径普遍过高”这个旧问题上。

#### 19.9.27 人工复核这 51 条“局部近音错排”后的判断

在继续往下拆之前，用户提醒了一个关键边界：

- 必须承认 `n-gram` 的能力上限；
- 不要把它拿去和大语言模型直接比较；
- 对尾部错例不要过度用力。

因此，这一步没有继续跑更慢的细分类脚本，而是直接对这批样例做人工复核，看是否真存在一个统一、低风险、可解释的可修模式。

人工复核后，这批样例大致可分为三类：

1. 语法功能词 / 虚词类
   - `时/是`
   - `的/地/得`
   - `它/他`
   - `这/着`
   - `自/字`
   - `其间/期间`
2. 局部实词近音替换
   - `街口/接口`
   - `微凉/微量`
   - `肩头/箭头`
   - `香脆/想脆`
   - `清朗/晴朗`
   - `小店/小点`
3. 较强语义 / 搭配依赖或文艺词汇弱势
   - `叶隙间/业席间`
   - `梧桐/无痛`
   - `扑簌簌/狡辩`
   - `征程/整成`
   - `放空/防控`

这三类的路线意义并不相同：

- 第一类很多本质上需要句法或更强语言理解，`n-gram` 只能有限改善，不能指望稳定修净；
- 第二类里有一小部分仍可能属于 `n-gram` 契约内的局部错排；
- 第三类则更接近语义、语体、常识或长搭配偏好，明显更像超出 `n-gram` 舒适区的问题。

因此，当前更稳妥的判断是：

- 这 51 条里并不存在一个“很统一、很低风险、很可解释”的总模式，足以支持继续做一轮全局调参；
- 如果继续做，也只能做极小范围、非常克制的局部实验；
- 在没有看到更强的统一信号前，当前主线应倾向于收束，而不是继续深挖这批尾部局部错例。

#### 19.10 阶段总结：这条路线是不是走错了？

结论需要分两层说：

1. **如果问的是当前这套实现形态**
   - 结论是：它已经证明自己**不如原版 `octagram`**；
   - 至少在当前数据和实验中，没有证据表明“先放大候选池，再靠 `witset_poet` 句级补救”能够追平或超过原版。
2. **如果问的是更大的总方向**
   - 结论不是“完全走错”；
   - 更准确地说，是：
     - `witogram + witset` 试图把更强句级信息引入输入法排序，这个方向本身仍有价值；
     - 但当前这条**把主要纠偏责任压到后段排序器**上的实现路线，理论上就先天吃亏。

#### 19.10.1 目前能确定的事实

- 当前线上 `C` 系列最好结果大致停在：
  - `Top-1 = 0.541528`
  - `Top-3 = 0.684385`
- 离线 `C0` 证明“正确契约”方向是有正信号的：
  - `Top-1 = 0.600000`
  - `Top-3 = 0.750000`
- 但即使是 `C0`，仍明显低于原版 `octagram` 基线 `Top-1 = 0.683333`
- 后续补的 `context`、`rerank`、`local rerank` 都没有带来稳定净收益

因此，当前最稳妥的判断是：

- **这条实现路线没有成功超越原版 `octagram`；**
- 并且这种落后并不只是“参数还没调到位”，而有更深的理论原因。

#### 19.10.2 为什么原版 `octagram` 反而更强

从理论层面看，原版 `octagram` 的强项不是“模型更复杂”，而是它做对了两件更适合输入法的问题：

1. **它把错误扼杀在更早的层级**
   - `octagram` 的 `credibility` 作用点更靠前；
   - 它在候选还没大规模扩张之前，就已经把一批低可信切分、低可信路径压下去；
   - 这非常符合输入法搜索的本质：
     - 候选空间极大；
     - 早期错误一旦放进头部，后面很难靠 rerank 再救回来。

2. **它优化的是“搜索阶段的可生存性”，不是“最终句子的事后解释”**
   - 输入法不是离线机器翻译，也不是开放式文本生成；
   - 它的关键不是把所有路径都生成出来再挑最自然的一句；
   - 而是在极小延迟下，让真正正确的路径在搜索过程中始终活着，并尽早领先。

`octagram` 虽然“粗糙”，但它的粗糙恰好贴合了这个任务：

- 它不强求后段拥有非常强的语言理解；
- 它先用简单、稳定、偏保守的上游先验，把明显坏路压掉；
- 这种 inductive bias 对输入法比“后面再细排一次”更有效。

#### 19.10.3 当前路线为什么理论上先天吃亏

当前这条路线的核心问题，不是句级信息“没价值”，而是它被放在了**太晚的位置**，还被赋予了**太重的职责**。

可以把当前路线概括为：

1. 上游先放进大量候选路径；
2. 中游继续保留很多本可更早淘汰的可疑路径；
3. 下游再希望 `witset_poet` / `witogram` 用句级打分把它们重新排对。

这在理论上有四个先天缺点：

1. **信用分配太晚**
   - 真正有用的信息是“这条拼写解释/切分路径本身是否可信”；
   - 但当前实现把大量纠偏责任放到句子形成之后；
   - 于是后段在做的，其实是替上游的错误决策擦屁股。

2. **搜索契约与评分契约错位**
   - 上游在按一种标准扩张候选；
   - 下游却试图用另一套更晚、更贵的标准推翻它；
   - 当候选池已经被污染时，后段排序器经常只能在“坏里挑稍好”，而不是看到真正干净的正确路径。

3. **Top-K/beam 截断不可逆**
   - 输入法搜索不是无限宽；
   - 一条正确路径如果在早期没有被保住，后面句级模型再强也无从发挥；
   - 所以“后面能看得更清楚”并不能弥补“前面已经把正确路放没了”。

4. **把不属于 LM 的问题推给了 LM**
   - 很多错误本质上是：
     - 拼写歧义问题；
     - 切分可信度问题；
     - 候选边先验问题；
   - 这些不应该主要由句级 `n-gram` 在最后一层解决。

#### 19.10.4 为什么 `C0` 有正信号，但仍打不过 `octagram`

`C0` 的意义很重要，因为它说明：

- 一旦把词图、路径和局部约束放进统一求解契约，确实比当前线上排序更合理；
- 也就是说，问题不在“句级信息完全没用”，而在“句级信息之前的契约不对”。

但 `C0` 仍打不过 `octagram`，理论上也不奇怪，因为它还缺三样关键东西：

1. **它仍继承了当前图和基础边权的历史包袱**
   - `C0` 只是离线求解器；
   - 它吃到的仍然是当前系统导出的词边、候选和基础分数；
   - 如果这些边权本身就没有把“可信切分/可信词边”表达好，统一求解也只能在一个不够好的底座上优化。

2. **它补的是“契约”，但没有真正补强“证据”**
   - `C0` 更像把现有证据重新组织得更合理；
   - 但它并没有从模型侧提供显著更强的新证据；
   - 而 `octagram` 的强项之一，正是它那套上游 `credibility` 已经在实践中形成了很强的有效偏置。

3. **尾部错误里有相当一部分本来就接近 `n-gram` 上限**
   - 前面人工复核已经看到：
     - 功能词混淆；
     - 文艺词汇弱势；
     - 语义/搭配依赖；
   - 这些并不是靠继续微调 `n-gram` 就能稳定解决的问题。

#### 19.10.5 这条路线真正“走错”的地方

因此，更准确的总结不是：

- “`witogram + witset` 整个方向错了”

而是：

- **把主要纠偏责任放在后段句级排序器，这条实现路线走错了；**
- **试图用后验 `n-gram` 打分去弥补上游候选契约问题，这个假设走错了；**
- **希望靠继续堆 `context` / rerank / 局部补丁去追平 `octagram`，这条线已经不值得继续深挖。**

#### 19.10.6 当前最合理的理论结论

到这一阶段，可以把理论结论正式收敛成下面几句：

1. `octagram` 胜出，不是因为它“更聪明”，而是因为它更符合输入法搜索的任务结构：
   - 早表达可信度；
   - 早淘汰坏路径；
   - 不把主要纠偏责任留到最后。
2. 当前 `witset_poet` 主导的后段补救路线，理论上就比原版吃亏：
   - 它把强信号放晚了；
   - 把错误留太久了；
   - 指望后段 `n-gram` 承担了不该承担的职责。
3. `C0` 证明“正确契约”方向仍然比当前线上形态更合理；
   - 但它还不足以证明这条大方向已经能超过原版。
4. 在承认 `n-gram` 能力上限的前提下，这一阶段最合理的结论不是“继续深挖尾部补丁”，而是：
   - 承认当前这条实现路线已经到头；
   - 把它作为一次有价值的反证；
   - 明确后续若再继续，必须从更上游的契约或更强证据入手，而不是继续在后段补救上加码。

#### 19.10.7 四条候选方案的当前状态总表

为了避免读到这里时仍不清楚“哪些方案已经实际跑过、结论是什么”，把本节四种方案收敛成下面的状态表。

1. **方案 A：前移为路径原始权重**
   - 对应后续 `E1` 的最小上游 prior 原型。
   - 已实现、已编译、已完成 `300` 条 baseline。
   - 结果：
     - `Top-1` 不变；
     - `Top-3` 略降；
     - `expected_not_found_count` 无改善。
   - 结论：
     - “把当前局部风险标签直接前移成静态减权 prior”这个抽象不成立。
     - 但这不等于“上游 contract 无效”，而是说明这版 prior 不是原版真正有效的 `credibility`。

2. **方案 B：joint-aware beam state**
   - 已做过把风险信号放入 beam / state 的尝试。
   - 结果：
     - 信号确实进入链路；
     - 但 `Top-1` 没有形成独立正收益。
   - 结论：
     - 仅把风险字段塞进状态，不足以改写主结果。
     - 若没有更强的竞争契约，它更像“更早知道风险”，而不是“更早保住正路”。

3. **方案 C：联合图一次性路径求解**
   - 已完成离线 `C0` 并得到第一个明确正信号。
   - 结果：
     - `C0` 明显优于当前线上基线；
     - 说明“统一图上的正确契约”本身是有价值的。
   - 但后续 `c0_ctx / c0_ctx_rerank / c0_ctx_local` 继续叠后段 `context` 后，没有稳定追平 `octagram`。
   - 结论：
     - 方案 C 证明“正确契约”方向是对的；
     - 但也同时证明“把更多后段 context 重新加回来”不是继续前进的主轴。

4. **方案 D：让模型本身提供更强分词证据**
   - 本阶段没有真正进入实现。
   - 结论：
     - 它仍是长期方向；
     - 但在搜索契约未重建前，不应优先投入。

## 20. 下一阶段技术设计草案：上游 prior + 正确契约

这一阶段不再以“继续优化 `witset_poet`”为目标，而是把系统重新拆成三层职责：

- 上游：尽早表达 `prior / credibility`
- 中游：按有限状态契约保留真正有希望的路径
- 下游：只在少量合理路径之间做句级精排

设计原则有四条：

1. 每一步都必须是**最小实验**
   - 先验证单个假设，再决定是否继续。
2. 每一步都必须能**单独止损**
   - 如果该步没有独立收益，就不把更多变量混进来。
3. 先验证**上游 prior 的价值**
   - 不再默认“句级 LM 自然会把它救回来”。
4. 句级 `LM` 只允许在最后承担**精排职责**
   - 不再负责大规模清洗候选池。

### 20.1 实验 E1：最小上游 prior 原型

#### 20.1.1 目标

验证一个最关键的问题：

- **只要把 `octagram-style credibility` 前移成上游 `path prior`，即使不改句级 LM，也能不能独立改善头部路径排序？**

这一步是整个新路线的第一道门槛。

如果答案是否定的，那么后面的“正确契约”也需要重新审视；如果答案是肯定的，说明后续值得继续投入。

#### 20.1.2 改动范围

只动上游 prior，不动 `witset_poet` 的句级精排逻辑，不引入新的 `context rerank`。

最小实现建议：

1. 在 `witset_translator` / 候选边生成阶段，为每条词边生成一个轻量 `path_prior`：
   - 来源只限于当前已验证相对稳定的上游信号：
     - `ambiguous joint`
     - 强负 `credibility`
     - 明显低可信的拼写切分
2. 将这份 `path_prior` 直接并入候选边或 `DictEntry` 的基础分数
3. `witset_poet` 保持尽量不变
   - 不再额外叠新后验特征
   - 只观察“上游先验前移”本身是否改写候选头部格局

#### 20.1.3 不做什么

- 不做新的句级补丁
- 不做新的 context 特征
- 不引入新的 rerank
- 不同时改 admission / beam state / 句级常数

#### 20.1.4 成功标准

最看重三件事：

1. `Top-1` 至少相对当前线上版出现**稳定正向变化**
2. `expected_not_found_count` 不显著恶化
3. 错例性质上，“正确路径存在但前面就被低可信路径压过”的比例下降

#### 20.1.5 失败信号

出现任一条，都应暂停继续往下叠：

- `Top-1` 不动或变差
- `expected_not_found_count` 明显上升
- 主要改善只体现在个别开发样例，而没有形成稳定趋势

#### 20.1.6 理论意义

E1 验证的是：

- 原版 `octagram` 的强项，是否可以先被抽象成“上游 prior”而非整套旧实现；
- 如果连这一步都没有独立价值，那么说明“回到 octagram 原则”也需要进一步收缩。

### 20.2 实验 E2：prior + 有限状态契约

#### 20.2.1 目标

验证第二个关键问题：

- **在上游 prior 已经前移的前提下，把线上搜索改成“每个 `pos + state` 只保留最佳路径”的有限状态契约，能不能在线上复现离线 `C0` 的主要正信号？**

这一步对应的是：

- 不是直接回到旧 `octagram`
- 而是把 `octagram` 的早期可信度原则，与 `C0` 证明过的统一求解契约结合起来

#### 20.2.2 改动范围

1. 以上游 prior 作为新的基础边权一部分
2. 将线上保留器明确改为：
   - 每个 `end_pos + approx_state` 只保留最佳路径
3. `approx_state` 必须保持最小：
   - 只允许包含少量真正与路径可生存性强相关的字段
   - 例如：
     - `end_pos`
     - 简化后的 `lm suffix` 或 token suffix
     - 极少量边界/可信度状态

#### 20.2.3 不做什么

- 不再扩很多状态桶
- 不把结构特征越堆越多
- 不同时引入新的句级 rerank
- 不试图在这一步就解决全部尾部错误

#### 20.2.4 成功标准

1. 线上 `Top-1` 明显高于当前 `0.541528`
2. 与离线 `C0` 的差距显著缩小
3. wall time 仍保持在可接受范围
4. 错例中“正确路径图里存在，但早期没活下来”的比例下降

#### 20.2.5 失败信号

- 准确率没有明显优于 E1
- 性能代价明显放大，但收益不匹配
- 主要变化仍只是候选池后段排序，而不是搜索保留顺序本身改写

#### 20.2.6 理论意义

E2 验证的是：

- 当前与原版真正拉开差距的关键，是否就是“正确路径在搜索过程中没被早点保住”；
- 如果 E2 仍然起不来，说明问题不只是 prior，也不只是契约，还可能在基础图和证据本身。

### 20.3 实验 E3：新契约下的轻量句级精排

#### 20.3.1 目标

只有当 E1/E2 都给出正信号时，才进入 E3。

E3 要验证的问题是：

- **在“坏路径已被上游 prior 和有限状态契约显著压缩”的前提下，句级 `LM` 作为小范围精排器，是否还能提供额外净收益？**

这一步的重点不再是“救火”，而是“锦上添花”。

#### 20.3.2 改动范围

1. 只在已经通过 E2 压缩后的少量合理路径之间运行句级比较
2. `witogram` 只提供轻量增量分或最终 rerank 分
3. 句级 `LM` 不允许改变太多候选生存关系
   - 只允许在主分数接近时拉开顺序

#### 20.3.3 不做什么

- 不再尝试用 `context` 去翻盘低分骨架
- 不再做整路径的 context 累积分
- 不再为尾部小样例反复调句级权重

#### 20.3.4 成功标准

1. 相对 E2 出现小而稳定的 `Top-1` 正收益
2. `fixed > regressed`
3. 新增收益主要集中在“同骨架、局部词选错”的场景

#### 20.3.5 失败信号

- 收益接近 0
- 仍然出现“低分骨架被 LM 翻盘”的老问题
- 主要回退集中在功能词、语义依赖或长距离理解问题上

#### 20.3.6 理论意义

E3 只是验证：

- 在正确契约已经成立后，句级 `n-gram` 是否还值得保留为一个小型精排器。

如果 E3 没收益，也不应把它视为路线失败，而应接受：

- `n-gram` 在这个位置上的最佳职责就是“可选精排”
- 而不是系统主心骨

### 20.4 为什么必须按 E1 -> E2 -> E3 的顺序

这个顺序是为了避免重回上一阶段的错误：

1. 先做 E1
   - 先确认上游 prior 是否真有独立价值
2. 再做 E2
   - 只在 prior 站住后，才验证正确契约
3. 最后才做 E3
   - 只把句级 LM 放在正确的位置上

如果反过来做，很容易再次出现：

- 上游没改好
- 中游没收干净
- 下游 LM 被迫继续救火

这正是上一阶段已经证明行不通的模式。

### 20.5 当前最推荐的启动项

如果只启动一个最小实验，优先级应当是：

1. **先做 E1：最小上游 prior 原型**

原因：

- 它最接近原版 `octagram` 真正有效的原则
- 改动边界最清晰
- 最容易独立验证
- 成败都最有信息量

当前不建议一上来就做：

- 大规模重写线上搜索器
- 继续补更多句级特征
- 再开一条新的 context 支线

### 20.6 阶段止损规则

为了避免再次在错误方向上越走越深，下一阶段应明确遵守下面的止损规则：

1. E1 若无独立正收益，则暂停整条新路线，重新审视 prior 定义
2. E2 若不能把线上表现明显拉近 `C0`，则暂停“线上工程化”，优先回头审视图和边权底座
3. E3 若没有稳定净收益，则接受句级 `n-gram` 只适合作为弱精排器，而不是继续加码

### 20.7 一句话版

下一阶段不是“回到旧 `octagram` 代码”，而是：

- 用 **`octagram` 的上游 prior 原则**
- 结合 **`C0` 证明过的正确契约**
- 再判断句级 `n-gram` 是否值得保留为一个小型精排器

这三步必须分开验证，不能再混成一团一起推进。

### 20.8 E1 当前已落地的最小实现

已开始直接按 `E1` 动手，实现刻意保持为一个最小闭环：

1. 在 `witset_translator.cc` 中新增了真正的上游 prior 注入：
   - 对 `WordGraph` 中每条 `(start_pos, end_pos)` 边，根据：
     - `edge_risk`
     - `edge_spelling_class`
     - `end_pos` 对应的 `vertex_risk`
   - 计算一个保守的 `upstream prior penalty`
   - 只对存在稳定风险信号的边，拷贝 `DictEntry` 后减小其基础 `weight`
2. 在 `witset_poet` 中把旧的 `joint_prior / joint_guidance` 后段惩罚改成默认关闭：
   - 新增 `use_joint_post_penalty` 开关，默认 `false`
   - 这样本轮 `E1` 不再是“上游 prior + 后段 joint 补罚”的混合实验

这一步的设计意图非常明确：

- 先验证“上游 prior 前移”本身有没有独立价值；
- 不再让 `poet` 末端再补一层相同含义的 joint 惩罚；
- 避免实验解释再次混淆。

### 20.9 E1 当前尚未完成的部分

当前只完成了实现落地，还没有进入结果验证阶段。

尚未做的事包括：

1. 编译并跑 `300` 条基线；
2. 复核：
   - `Top-1 / Top-3`
   - `expected_not_found_count`
   - 典型错例是否体现出“正确路径更早领先”；
3. 判断这版 prior 是否过强或过弱。

因此，现阶段应把 `E1` 状态记为：

- **已实现**
- **未验证**

### 20.10 E1 第一轮真实结果：先触发性能/推进性回归

在用户授权后，已继续按“实现 + 跑基线合并一步”的方式执行 `E1`：

1. 先按工作区规则执行 `outwit-windows/build_and_deploy.bat`
   - 编译与部署链路通过
   - 无新的编译错误
2. 再直接运行 `300` 条 baseline

但这轮并没有进入准确率比较，而是先暴露出一个更基础的问题：

- `E1` 当前版本在一档 baseline 下**跑不完**

第一次尝试：

- `--snapshot-timeout-seconds 60`
- 在第 19 条长输入
  - `liangpangdefaguowutongxiangshiwushengdeshouhuzhe`
  - 等待 snapshot 超时

为了确认这不是单纯“60 秒不够”，又做了第二次重跑：

- `--snapshot-timeout-seconds 120`
- 结果反而更早就在第 1 条 case 超时
- `last_seen_input = jinchens`

这说明当前 `E1` 的首要问题不是：

- 精度是否提高；
- 或 `Top-1 / Top-3` 是否优于当前线上版。

而是：

- 它首先触发了**严重的性能/推进性回归**；
- baseline 连完整跑完都做不到。

当前工件也支持这一判断：

- `baseline_run_metadata.json`
  - `completed_text_steps = 0`
  - `status = interrupted`
- `witset_local_snapshot.jsonl`
  - 只推进到 `jinchens`
  - 候选记录仍在持续写出

因此更像是：

- 查询显著变慢；
- 或候选推进过程中出现了不可接受的性能退化；
- 而不是构建失败或 snapshot 根本没有工作。

### 20.11 对 E1 的当前判断

到这一步，`E1` 的状态应从“已实现、待验证”更新为：

- **已实现**
- **已编译**
- **baseline 失败**

而且失败的层级比预期更早：

- 不是“效果不好”；
- 而是“连可接受的一档基线都跑不完”。

这对后续顺序的含义是：

1. `E1` 仍然是正确的第一步实验；
2. 但它当前版本还不具备进入精度比较的资格；
3. 下一步必须先查清：
   - 是上游 prior 注入本身过重；
   - 还是拷贝/改写 `DictEntry` 的实现方式造成了查询性能大幅退化；
   - 再决定是否继续保留这版 prior 定义。

### 20.13 对 E1 的最终结论

到这一步，`E1` 可以正式定性为：

- **实现完成**
- **编译通过**
- **baseline 已完整验证**
- **结果不成立**

也就是说，作为“下一阶段第一步”的最小实验，当前这版 `E1` 没有通过门槛。

按照本章前面已经写明的止损规则：

- 如果 `E1` 没有独立正收益，就不应该直接继续叠加 `E2 / E3`；
- 而应先承认：**这版 prior 定义本身没有提供足够的信息量**。

这并不自动否定“回到 `octagram` 原则”这条总方向，但它明确否定了当前这一版最小 prior 设计：

- 单靠当前的
  - `edge_risk`
  - `vertex_risk`
  - `edge_spelling_class`
- 以前移减权的方式注入基础边权，并不能独立改善当前线上表现。

### 20.14 E1 失败说明 prior 抽象错在什么地方

`E1` 失败并不等于“上游 prior 这个想法失败”，更准确地说，它说明：

- **我们从 `octagram` 身上抽出来的这版 prior，不是它真正有效的那个 prior。**

理论上，至少错在下面五点。

#### 20.14.1 我们抽出来的是“风险标签”，不是“真实 credibility”

当前 `E1` 主要使用的是：

- `edge_risk`
- `vertex_risk`
- `edge_spelling_class`

这些信号当然和上游可信度有关，但它们更像是：

- 风险提示；
- 错误倾向标签；
- 局部疑点标记。

而 `octagram` 真正强的地方，大概率不是“看见风险就统一减一点分”，而是：

- 对候选路径来源、拼写解释、切分方式、路径形成过程本身，有一套更完整的 `credibility` 组织方式；
- 这些信息不是简单压缩成三个局部风险字段后还能无损保留的。

也就是说：

- 我们在 `E1` 里抽出来的是 `credibility` 的**影子**
- 不是它真正可工作的主体

#### 20.14.2 这版 prior 只有“减坏路”，没有“抬好路”

当前 `E1` 的做法本质上是：

- 看到有风险的边，就减一点基础分。

这是一种**纯负向 prior**。

但一个真正有力的上游 prior，通常不只是：

- 惩罚低可信路径

还应该能：

- 明确偏置高可信路径；
- 让正确路径更早形成领先；
- 在同一组竞争路径中，把“更像正路”的那条主动抬起来。

如果只有负向惩罚，会遇到两个理论问题：

1. 若一组竞争候选都带有相似风险标签
   - 那么大家一起被减分，排序关系未必改变。
2. 若真正正确路径并没有得到正向支持
   - 只是“别人被打一点”，往往不足以把它稳定推到前面。

这正符合 `E1` 的结果：

- `Top-1` 不动；
- `Top-3` 略降；
- 说明这类减权没有形成真正可用的判别力。

#### 20.14.3 这版 prior 是静态加法，不是相对竞争式 prior

`octagram` 的有效偏置，很可能是**竞争式**的，而不是单纯的**绝对式**惩罚。

也就是说，它真正回答的问题更像是：

- 在这组互相竞争的解释里，哪条更可信？

而当前 `E1` 回答的问题是：

- 这条边自己看起来危险不危险？

这两个问题不一样。

输入法搜索里，很多关键分歧并不是“某条边绝对很坏”，而是：

- 两条边都能成立；
- 但其中一条更像是输入法真正应该保留的路径。

例如：

- 同一段输入下的不同切分；
- 同一组近音候选的不同词边解释；
- 简拼 / 模糊音 / 补全路径之间的竞争。

这类问题如果没有“相对比较”能力，只做独立减分，往往改不了排序主结果。

#### 20.14.4 这版 prior 仍然太局部，触不到当前主错因

从前面的错例分析已经知道，当前剩余错误主要集中在：

- 局部近音词错排；
- 多词组合总分偏差；
- 长句搭配/语义超出 `n-gram` 舒适区。

而当前 `E1` 注入的 prior 主要作用在：

- 单条 edge；
- 单个终点 vertex；
- 单个 spelling class。

这意味着它更像是在调：

- “这条边像不像可疑边”

但当前真正的大头错误，很多是：

- 多条边组成的整体路径竞争；
- 同骨架内的词选错；
- 局部都合理，但整体组合不对。

所以它天然只能触到一小部分问题。

这也解释了为什么：

- `expected_not_found_count` 没改善；
- 错句类型也没出现新的结构性变化。

#### 20.14.5 我们把“何时生效”前移了，但没把“信息形态”改对

`E1` 的确把 prior 从 `poet` 后段前移到了基础边权，这一步在位置上是对的。

但位置前移，不等于信息就自动变成正确 prior。

更准确地说，`E1` 做到的是：

- **把旧的风险信息更早使用**

而不是：

- **把 `octagram` 真正有效的 credibility 重新构造出来**

所以 `E1` 的失败，理论上更像是在说明：

- 错的不只是“信号放太晚”
- 还错在“当前这批信号本身信息量不够，且形态不对”

### 20.15 由 E1 失败推回去，`octagram` 真正可能强在哪里

`E1` 的反证其实很有价值，因为它帮我们把 `octagram` 的强项缩小到了更具体的范围。

当前更合理的推断是，`octagram` 的强项大概率具有以下特征：

1. **不是单纯的风险惩罚，而是路径可信度建模**
   - 它更像是在描述“这条路径为什么像正路”
   - 而不是“这条边哪里可疑”
2. **不是孤立 edge 打分，而是竞争组内的相对偏置**
   - 真正有用的是“在这组候选里优先谁”
   - 而不是给每条边独立加一个静态罚分
3. **不是纯负向信号，而是同时包含正向支持**
   - 既能压错路
   - 也能扶正路
4. **不是只看局部标签，而是与搜索保留行为深度耦合**
   - 它的价值可能体现在“谁更早活下来”
   - 而不只是最终句子分数多几分少几分

### 20.16 对下一步的理论含义

所以，`E1` 失败后，最重要的理论更新不是：

- “上游 prior 这条路不行”

而是：

- “不能再把 `octagram` 的 prior 误简化成几项局部风险罚分”

如果后面还要继续沿“回到 `octagram` 原则”这条大方向走，下一步需要回答的理论问题应当是：

1. `octagram` 的 `credibility` 到底在区分什么竞争关系？
2. 它真正依赖的是哪些上游信息，而不是哪些局部风险标签？
3. 它是否本质上是一种“竞争组归一化/偏置”机制，而非简单加减分？

只有把这几个问题回答清楚，后续新的 prior 设计才有可能比 `E1` 更接近原版真正有效的部分。

## 21. 阶段收束与新路径启动（2026-05-19）

### 21.1 为什么在此处给旧子路线画休止符

这一节不是重复 `WORKLOG`，而是把“项目级路线决策”落成可执行约束。

本轮连续实验后可以确认：

1. 后段局部修分线的信息增益已经快速衰减。
2. 新增 patch 虽可解释个别单句现象，但难以跨样本泛化。
3. 长 continuation 的主竞争不再受局部 bridge 门控主导，而受错误强 continuation 吸引子主导。

因此，本计划文档将“末端修分追平 `octagram`”标记为**阶段性封口**，不再作为主执行路线。

### 21.2 封口范围（从现在起默认不再追加）

除非后续有全新证据，否则不再继续堆以下类型改动：

1. `shared-prefix` 批内保护类补丁
2. `clean bridge` / `debt-gated clean bridge` 及其变体
3. 仅在 `witset_poet` 末端追加的 `LM comparability` 小门控
4. 以“单句局部回升”作为保留依据的后段 patch

### 21.3 保留什么（作为下一阶段资产）

旧阶段并非“失败作废”，应保留三类可迁移资产：

1. **证据资产**
   - `B/C` 分桶结论、`C1/C2` 细分、continuation 梯子、`octagram 对/当前错` 锚点。
2. **流程资产**
   - 单句因果定位 -> 小型代表集 smoke check -> 再决定是否扩大验证。
3. **边界资产**
   - 已确认“打不到问题面”的 patch 类型清单，用于防止重复试错。

### 21.4 新路径目标：插件化 `credibility contract`

为兼容 Rime 生态，下一阶段默认采取“插件内复刻有效契约”而非修改 `librime` core：

1. 不追求逐行复刻 `syllabifier` 源码。
2. 追求复刻其真正有效的输出形态：
   - path credibility / path debt ledger
   - ambiguous joint debt
   - correction / completion debt
   - fallback / OOV debt
   - path compactness / provenance
3. 让上述 ledger 尽量在候选进入 `poet` 前参与：
   - 生存关系
   - 基础边权
   - 竞争组相对偏置

### 21.5 新阶段的执行门槛

为避免重回“后段补丁循环”，新路径采用强门槛：

1. **门槛 A：实现门槛**
   - 新增逻辑必须主要落在上游候选契约层，而不是 `poet` 末端补分层。
2. **门槛 B：验证门槛**
   - 先通过固定小型代表集 smoke check，至少满足：
     - `improved > 0`
     - 无明显回退样例
3. **门槛 C：扩展门槛**
   - 通过小集后才进入更大基线；未通过则止损，不叠下一层变量。

### 21.6 与路线 B 的关系（避免方向误读）

本次收束不是“路线 B 终止”，而是“路线 B 进入新阶段”：

1. 阶段一（已完成）：证明后段重排可解释、可验证，但上限受制于上游契约缺失。
2. 阶段二（启动中）：重建插件化 `credibility contract`，先追平 `octagram` 的任务结构优势。
3. 阶段三（后续）：在契约成立后，再发挥 `witogram` 的统一句级精排优势，争取超过 `octagram`。

### 21.7 本节一句话

从本节起，本计划的默认执行基线是：

- **暂停“后段补丁追平”**
- **启动“插件化上游契约重建”**
- **先追平，再超越**

### 21.8 本次对话新增路径的实现结果与结论总表

下面这张“路径状态表”用于补齐本次对话期间真正实现、编译、回放过的各条子路径，避免信息只留在 `WORKLOG`。

1. **`all_requests` 内部的 shared-prefix family protection**
   - 做法：
     - 在 `all_requests` 排序后、`batch_selected` 前，对同 shared-prefix family 的 reparse 路径做批内保护。
   - 结果：
     - 两次单例回放完全不动。
   - 结论：
     - 竞争对象根本不在同一 `all_requests` 批次里；
     - 这条实现层级放错，已回退并封口。

2. **`target_pool / final_pool` 合流探针**
   - 做法：
     - 给 `states[end_pos] / target_pool / final_pool` 增加最小 instrumentation。
   - 结果：
     - `第一 + 展示`
     - `第一展 + 示`
     - `第一站 + 是`
     - 并未在共享 `state_key` 上发生 replace / reject。
   - 结论：
     - 主竞争不在同态去重；
     - 而是在最终 `beam_score` 上正面对打。

3. **`Base` 主轴 carry-over 来源 probe**
   - 做法：
     - 把前缀继承由 `candidate->weight` 临时换成 `candidate->cumulative_base`。
   - 结果：
     - 各条目标路径整体抬高，但相对差距几乎不变。
   - 结论：
     - “历史总分滚雪球”不是唯一根因；
     - 单换 carry-over 源头，无法扶正 `第一站是*`。

4. **`Base` 主轴移除 `lm_score_scaled` probe**
   - 做法：
     - 临时拿掉 `Base` 中 `lm_total_weight_ * lm_score_scaled`。
   - 结果：
     - `第一站是*` 家族在 continuation 上明显翻身；
     - 但 `diyizhanshi` 当步仍未直接翻成 `top1`。
   - 结论：
     - `lm_score_scaled` 是最大的主压制项；
     - 但不是唯一项。

5. **只屏蔽 `adjustment` 里的手工结构项**
   - 做法：
     - 只保留 `dict_score_norm + lm_avg`，临时关掉 `whole / fragment / length / tail / oov / boundary / octagram / early_* / prefix_anchor_*`。
   - 结果：
     - 主排序几乎不变。
   - 结论：
     - 剩余压制不主要来自手工结构 adjustment。

6. **`lm_avg` 与 `dict_score_norm` 二分 probe**
   - 做法：
     - 分别只移除 `lm_avg`、只移除 `dict_score_norm`。
   - 结果：
     - 去掉 `lm_avg` 后，`第一站是*` 相对前移；
     - 去掉 `dict_score_norm` 后，主差距几乎不变甚至略差。
   - 结论：
     - 次级残余压制项主要是 `lm_avg`；
     - `dict_score_norm` 不是主压制项，更接近补偿项。

7. **两段式 `LM comparability` 原型**
   - 做法：
     - 第一刀：`whole_first_word clean bridge` 的 `LM release`。
     - 第二刀：再叠“短前缀 + 两字 fallback continuation”统一缩放。
   - 结果：
     - 第一刀单句有正信号；
     - 第二刀方向失真，把 `敌意展示 / 地衣展示` 这类 wrong family 顶回前排。
   - 结论：
     - “clean bridge”命中了真实局部病理；
     - 但“所有短前缀两字 fallback continuation 一刀切缩放”是错误抽象。

8. **最强前缀 companion gate**
   - 做法：
     - 只对当前 `source_pool` 最强前缀开放第二刀 `LM release`。
   - 结果：
     - 能把 `第一站是` 拉回 `top3`；
     - 也能压住 `敌意 / 地衣` 错前缀族；
     - 但仍打不穿 `第一战士*` 主簇。
   - 结论：
     - 它只修掉“wrong family 抢位”问题；
     - 没有触及最深主竞争。

9. **从单句切到 21 条小型代表集**
   - 做法：
     - 以 `_shared_prefix_eval_excerpt.txt` 做 smoke check。
   - 结果：
     - `clean bridge`：`improved = 0 / worsened = 1`
     - `prefix debt gate`：`improved = 0 / worsened = 1`
   - 结论：
     - 单句正信号不能直接外推；
     - 这整条 `clean bridge` 支线都没有通过泛化门槛，应封口。

10. **continuation 梯子**
    - 做法：
      - 把 `第一站是一座古老的小镇` 拆成 `diyizhanshi -> diyizhanshiyizuogu...` 的逐步输入梯子。
    - 结果：
      - 主差距不是在 `小镇 / 镇` 最后一步才形成；
      - 而是在 `yizuo -> yizuogu` 阶段迅速爆开。
    - 结论：
      - 长句主问题不是局部 bridge；
      - 而是错误 continuation `第一战士已作古...` 在当前可见文本上天然更顺。

### 21.9 由这些结果推出的最终项目级结论

把第 19 节历史方案与第 21.8 节新增实验放在一起，当前可正式收敛为下面几句：

1. **路线 B 没有被否定**
   - `witogram` 负责 `LM` 特征、`witset_poet` 负责句级精排，这个总方向仍值得保留。
2. **“继续在 `witset_poet` 后段补局部修分追平 `octagram`”已阶段性走到头**
   - 不再值得继续堆：
     - `shared-prefix` 小门控
     - `LM comparability` 局部 release
     - `clean bridge`
     - `debt-gated clean bridge`
     - 以及同类末端 patch
3. **真正该继续的是插件化 `credibility contract`**
   - 不是机械复刻 `librime` core；
   - 而是在插件里重建：
     - path credibility / path debt ledger
     - ambiguous joint debt
     - correction / completion debt
     - fallback / OOV debt
     - path compactness / provenance

### 21.10 后续默认执行约束

为了防止后续又回到“单句 patch 循环”，从本节起默认遵守以下约束：

1. 新原型优先落在候选进入 `poet` 前的契约层，而不是 `poet` 末端补分层。
2. 单句只能用于因果定位，不能作为保留原型的最终依据。
3. 任何新原型都必须先通过固定小型代表集 smoke check，再决定是否进入更大基线。
4. 若新路径不能明确改善“正确路径更早活下来”，则不进入下一层叠加实验。
