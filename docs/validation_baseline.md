# Witogram 基线验证规范

## 1. 目的

本文档用于定义 `witogram` 路线 B 推进过程中的基础验证规范。

目标不是一次性证明新架构已经全面优于 `octagram`，而是先建立一套稳定、可重复、可扩展的验证基线，确保后续每次改动都能回答以下问题：

1. 本次改动是否让候选排序更合理？
2. 本次改动是否修复了已知问题？
3. 本次改动是否引入了新的退化？
4. 本次改动是否显著增加了计算成本？

---

## 2. 样例来源

当前统一采用以下文件作为基础测试语料：

- [test_sentence.txt](file:///c:/Code/outwit/witset-worker/tests/test_sentence.txt)

这份文件应作为**每次验证都必须全量运行**的主测试样例库。

主测试语料中包含：

- 长句
- 歧义句
- 文学性表达
- 新闻/说明文风格文本
- 高频同音冲突场景
- 对语言模型上下文依赖较强的文本

它适合作为路线 B 第一阶段的统一评测语料。

---

## 3. 基线验证目标

在路线 B 的早期阶段，验证重点不是“大模型重排”或“最终语义理解”，而是以下基础能力：

1. **候选排序基础正确性**
   - 在常见同音冲突中，合理候选应优先于明显不通顺候选。
2. **上下文约束有效性**
   - 长句中后续词语应受前文影响，而不是只由单字高频主导。
3. **打分分项可解释**
   - 每个候选需要能拆解出主要分数来源。
4. **改动可回归**
   - 新版本不应修一个问题又破坏一批旧样例。

这里的验证边界需要特别明确：

- 当前评测对象是 **`witogram + Rime 本地候选排序链路`**
- 不是 `OutwitSettingsServer` 的后端 PPL 重排序
- 不是 Beam Search 或大模型约束解码

也就是说，本阶段要回答的问题是：

- `witogram::Query()` 本身是否合理
- 它和 Rime 字典权重的融合是否合理
- 本地排序为什么会把错误候选排在前面

---

## 4. 样例分类建议

后续从主测试语料中抽取样例时，建议至少维护以下几类集合。

### 4.1 高频同音歧义集

目标：

- 观察语言模型是否能压制明显不合理的高频单字组合。

典型关注：

- 身后 / 神后
- 身旁 / 神旁
- 澄澈 / 诚澈
- 可以 / 棵以

### 4.2 长句上下文依赖集

目标：

- 验证语言模型是否真正利用了前文上下文。

特点：

- 句子长
- 中后段候选依赖前文语义或搭配
- 单纯依靠字频时容易选错

### 4.3 文学表达集

目标：

- 观察模型在较弱模板化、较强修辞和较高语言流动性文本中的表现。

来源：

- 主测试语料中包含大量叙事和议论段落，可从中选取。

### 4.4 新闻说明文集

目标：

- 验证在更规范、更高频的语言分布下，模型是否稳定。

### 4.5 对抗回归集

目标：

- 专门收录每次开发中暴露出的“经典错误句”。

要求：

- 任何新改动都必须在全量测试中覆盖这一组
- 一旦某个错误被修复，就永久保留在全量测试语料或其派生回归语料中

---

## 5. 每次验证至少要输出什么

针对每个测试输入，建议至少输出以下信息：

1. 输入文本
2. 候选列表
3. Top-1 候选
4. Top-3 候选
5. 每个候选的本地分项分数
   - `Dict`
   - `LmRaw`
   - `LmScaled`
   - `Base`
   - `Pen`
   - `Total`
6. 候选是否命中预期

当前代码尚未全部具备这些输出项，因此本文档也作为后续改造目标说明。

## 6. 验证结果建议格式

建议每次验证至少产出以下文件：

### 6.1 `witset_local_snapshot.jsonl`

记录每次本地造句完成后的候选顺序与本地分项分数。

注意：

- 当前推荐格式是 **JSONL（每行一条 JSON 记录）**
- 目的不是只保留最后一次结果，而是为了支持整份 `test_sentence.txt` 跑批时的**累计采集**
- 后续汇总脚本会直接读取这份 JSONL 文件生成统计结果

建议结构如下：

```json
{
  "input": "nianshaodeqinggan",
  "preceding_text": "那时的我，总是刻意走在她的身后或身旁，",
  "llm_level_flags": {
    "llm_level_1": true,
    "llm_level_2": false,
    "llm_level_3": false
  },
  "candidate_count": 3,
  "candidates": [
    {
      "rank": 1,
      "text": "年少的情感轻轻浅浅，",
      "debug": " [Debug] Base:-84.69 Pen:0.00 Total:-84.69 Dict:-12.34 LmRaw:-31.43 LmScaled:-72.35"
    }
  ]
}
```

当前仓库里，这份快照由 `witset_translator` 的本地导出逻辑生成；它只反映本地候选与本地打分，不包含后端 PPL 结果。

### 6.2 `metrics.json`

记录全量语料上的本地排序汇总指标，例如：

- Top-1 Accuracy
- Top-3 Accuracy
- Pairwise Accuracy
- 平均耗时
- P95 耗时

### 6.3 `regression_report.md`

用人类可读的方式总结：

- 哪些样例变好了
- 哪些样例退化了
- 哪些样例结果没有变化

建议至少包含：

- 本次版本标识
- 相比上一版本的 Top-1 变化
- 高频同音错误是否减少
- 新出现的明显退化样例

## 7. 评测执行原则

当前不采用“最小验证集优先”的策略。

执行原则如下：

1. **每次改动都跑全量 `test_sentence.txt`**
2. 不以少量固定样例替代全量评测
3. 只有全量结果通过，才认为本次改动具备继续推进的基础
4. 典型错误样例可以额外单独观察，但不能代替全量结果

这样做的好处是：

- 避免在少量样例上过拟合
- 避免“局部看起来变好、整体其实退化”
- 让路线 B 的推进始终建立在完整语料表现之上

---

## 8. 第一阶段的最低验收标准

在路线 B 的早期阶段，不追求一开始就全面优于 `octagram`，但至少应满足：

1. 能稳定复现同一份全量测试语料的验证结果。
2. 能解释每个候选为什么排在当前位置。
3. 关键经典错误句不再只能靠手工试打判断。
4. 改动前后能清楚比较“谁变好了，谁变差了”。

---

## 9. 与 README 的关系

`README.md` 应始终反映当前真实能力。

本验证规范的作用，是为 README 的对外表述提供事实依据：

- 哪些能力已经完成
- 哪些能力仍在推进
- 哪些宣传语可以保留
- 哪些宣传语必须谨慎

换言之，README 不应领先于验证结果。

## 10. 下一步实施建议

基于当前基线规范，下一步建议优先推进：

1. 在 `witset_poet` 中拆分并输出显式分项分数
2. 在 `witset_translator` 中启用本地快照导出开关
3. 使用全量 [test_sentence.txt](file:///c:/Code/outwit/witset-worker/tests/test_sentence.txt) 驱动输入流程，生成累计的 `witset_local_snapshot.jsonl`
4. 使用 `tools/summarize_local_snapshot.py` 基于累计快照整理 `metrics.json` 与 `regression_report.md`

建议使用的配置项：

```yaml
translator:
  debug_dump_local_snapshot: true
  debug_local_snapshot_path: "C:/Users/Bing/AppData/Roaming/witty/debug/witset_local_snapshot.jsonl"
  debug_dump_local_graph_snapshot: false
```

只有完成这些基础设施，后续转换脚本、评分契约和模型训练的改动才真正可控。
