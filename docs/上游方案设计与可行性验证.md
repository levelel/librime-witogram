## 候选规则草案

### 1. 第一层：强负向 gate

只要命中下面任一类，优先视为“当前路径不应被当成健康主轴”：

1. `family_tag = family_drifted` 且 `continuation_tag = exact_but_wrong_family`
2. `risk_assist_tag = shared_axis_clean_dead_tail`

理由是：

- 第一类说明错误已经在 `family` 层坐实，不需要再等 `risk_assist` 补证据
- 第二类说明虽然还挂在 shared-axis 上，但已经没有 downstream exact completion 支撑，更接近“死尾巴”而不是“可恢复分支”

在只读草案里，这两类都应进入**强负向名单**。

### 2. 第二层：中等负向提示

命中下面这类时，不直接当 hard gate，但应作为强烈的负向观察信号：

1. `risk_assist_tag = legal_clean_unconfirmed`

这类标签的含义更像：

- continuation 还合法
- 当前边本身也不一定有 risk
- 但 `source_axis` 已经没有稳定落点，属于“还没彻底坏掉，但主轴已经不稳”

因此它更适合被记为**中等负向提示**，后续只有在多句复核里稳定命中，才考虑继续升格。

### 3. 第三层：弱辅助，不得直接升格

当前明确不能直接当正向资格或强负向 gate 的，是：

1. `risk_assist_tag = shared_axis_clean_supportive`

它的真实含义目前更像：

- shared-axis 上还存在 exact completion 支撑
- 但这并不等于“它就是正确主轴”

因为这类组合已经在 `ok / unstable / bad` 三个桶里都出现，所以它只能保留为**弱辅助读数**：

- 可以作为“还值得继续看”的证据
- 不能直接奖励
- 也不能单独判死刑

### 4. 第四层：正向健康信号

当前最接近“健康主轴”读数的是：

1. `path_tag = primary_path_eligible`
2. `source_axis_tag = source_axis_eligible`

- `primary_path_eligible`

## 为什么不能直接硬塞进现有 validated continuation bias

我把 `witset_translator.cc` 的链路重新对了一遍：

1. 真正影响 `candidate->weight` 的合同入口都在 `WordGraphRewriter::Apply()`
2. 当前和这次 guard 最接近的现成入口，确实是：
   - `ComputeTranslatorValidatedContinuationBias()`
3. 当前 snapshot/export 里的标签链路是：
   - `ClassifyContinuationTag()`
   - `ClassifyPrimaryPathTag()`
   - `ClassifySourceAxisTag()`
   - `ClassifyRiskAssistTag()`

但这里有一个关键工程约束：

- `wrong_family_exact + legal_but_path_unconfirmed` **并不总是落在同一个 segment 上**

已经确认的两个典型 case 就说明了这一点：

1. `从校门口一路走去`
   - `校门口` 命中 `wrong_family_exact`
   - `一路` 才命中 `legal_but_path_unconfirmed`
2. `也带着一种不可挽回的流逝`
   - `不可挽回` 先命中 `legal_but_path_unconfirmed`
   - `流逝` 才命中 `wrong_family_exact`

这意味着：

- 这条 guard 不是单 candidate 即时可判的局部规则
- 它本质上是一个**跨 segment 的联动资格**

而 `ComputeTranslatorValidatedContinuationBias()` 当前只看：

- 当前 `prefix_state`
- 当前 `candidate`
- 当前 edge 的 family best / exact best
- 当前 edge risk

它没有直接表达“同一句别的 segment 也命中过 `legal_but_path_unconfirmed`”这个能力。

所以如果把新 guard 直接揉进这个函数，会导致两个问题：

1. **语义污染**
   - 原本 validated continuation 只在 clean family + strong exact 的局部合同上做 boost / penalty
   - 把跨 segment 联动硬塞进去，会让函数职责变脏
2. **实现上会偷换问题**
   - 为了在单函数里拿到联动信息，最后很可能退化成某种不可靠的局部近似
   - 这样容易把当前样本里干净的联动，落成一个真实逻辑上并不等价的 patch

## 当前最小原型的正确挂点

因此，最小原型更合理的挂法应该是：

### 1. 挂在 `WordGraphRewriter::Apply()` 里

理由：

- 它本来就是当前 upstream rewrite 真正修改 `candidate->weight` 的地方
- `bridge / exact_family / validated_continuation` 都在这里汇合
- 在这里新增一个独立的 linked-guard bias，改动面最小，也最容易做开关

### 2. 新增独立 helper，而不是改写现有 helper 语义

建议最小新增一个类似这样的函数：

```cpp
static double ComputeTranslatorLinkedGuardBias(...);
```

它的职责只做一件事：

- 判断当前 candidate 是否命中
  - `wrong_family_exact + legal_but_path_unconfirmed`
- 若还叠加 `shared_axis_clean_dead_tail`
  - 再提高负向强度

而不是把这些逻辑揉进：

- `ComputeTranslatorValidatedContinuationBias()`

这样好处是：

- validated continuation 仍保持原来的“clean family continuation 合同”职责
- linked guard 作为独立实验原型，可以单独开关、单独调参、单独回滚

## 但它不是纯局部规则，所以最小原型需要一个“小状态层”

这次设计里最重要的新判断是：

- 即便只做“最小原型”，也不能假装这条规则是单 segment 局部规则

原因前面已经确认：

- `wrong_family_exact` 和 `legal_but_path_unconfirmed` 可能出现在前后不同 segment

所以最小原型至少需要一个很薄的状态层，用来回答：

- 当前 candidate 所在路径，上游或下游是否已经出现过 `legal_but_path_unconfirmed`

### 最小可行状态层建议

最小可以做成“两端一薄层”：

1. **前向 prefix guard state**
   - 从开头推进到当前 `start_pos`
   - 记录 best exact prefix 上是否已经出现过：
     - `legal_but_path_unconfirmed`
     - `shared_axis_clean_dead_tail`
2. **后向 tail guard support**
   - 从当前 `end_pos` 往后回看
   - 记录从这个位置开始的 best exact tail 上是否还能命中：
     - `legal_but_path_unconfirmed`
     - `shared_axis_clean_dead_tail`

这样当前 candidate 在计算 linked guard 时，只要检查：

- 当前 candidate 是否 `wrong_family_exact`
- prefix side 是否已见 `legal_but_path_unconfirmed`
- 或 tail side 是否还能接到 `legal_but_path_unconfirmed`

就能覆盖当前已确认的两类命中形态：

1. `wrong_family_exact` 在前，`legal_but_path_unconfirmed` 在后
2. `legal_but_path_unconfirmed` 在前，`wrong_family_exact` 在后

## 为什么这是“最小”而不是过度设计

因为当前现场其实已经具备了大部分需要的数据：

- `BuildBestPrefixStates()`
- `BuildContinuationPathSummaries()`
- `BuildExactAxisPrefixStates()`
- `BuildExactCompletionSupports()`

也就是说：

- 这不是要新造一套完全独立的图算法
- 而是在现有 rewrite / snapshot 已经使用的 prefix / tail 口径上，再加一个很薄的 guard state

所以最小原型在工程上可以压成：

1. 新增一层很薄的 guard state helper
2. 新增一个 linked guard bias helper
3. 在 `WordGraphRewriter::Apply()` 里把它和现有 bias 一起累加

## 最小配置面建议

当前 `WordGraphRewriteConfig` 里只有：

- `upstream_edge_prior_weight`
- `upstream_path_prior_weight`
- `upstream_validated_continuation_weight`

为了让原型最小，我不建议一开始就加一堆新参数。

更合理的最小配置面是：

1. 新增一个权重：
   - `upstream_linked_guard_weight`
2. 继续复用现有总开关：
   - `enable_upstream_edge_prior`

## 为什么不是直接改 `witset_poet`

我把 `witset_poet.cc` 的主链重新对齐后，确认：

1. 真正直接影响句级排序的主链确实在 `WitsetPoet`：
   - `upstream_path_prior_penalty`
   - `joint_prior_penalty`
   - `joint_guidance_penalty`
   - `beam_merge_penalty`
   - 以及一整组 early bonus / penalty
2. 这些项确实比后面的 search/merge 更“早”，尤其：
   - `upstream_path_prior_penalty` 直接进入 `base_score`

但这里有一个本体约束：

- `linked_guard` 当前成立的核心资格是：
  - `wrong_family_exact + legal_but_path_unconfirmed`

而 `wrong_family_exact` 这个信号，本质上依赖：

- 同一 `start -> end` family 内部的 exact 候选相对关系
- `best exact / second best exact / family clean vs drifted` 这种图级比较

这些信息在 `WitsetPoet` 的逐条 beam expansion 现场并不天然可见。

`poet` 现场更擅长处理的是：

- `local_edge_risk`
- `end_vertex_risk`
- `edge_spelling_class`
- `used_char_fallback / matched_whole_word`
- prefix 累积 fallback / OOV / joint hits

也就是说：

- `poet` 很适合处理“连续型路径风险”
- 但不适合直接表达“这个 exact 候选在同 family 内属于 wrong family”这种相对资格

## 调用顺序上的关键确认

我重新核对了调用顺序后，发现这个结论非常重要：

1. `translator` 先构建 `WordGraph`
2. 然后执行：
   - `WordGraphRewriter(rewrite_config).Apply(ledger, &graph);`
3. 之后才进入：
   - `poet_->MakeSentences(...)`

也就是说：

- 我们并不是被迫只能在 `poet` 里前移
- **`WordGraphRewriter::Apply()` 本身就已经处在 poet 之前**

因此“前移”的真正含义应该改写成：

- **不要在 `Apply()` 里对单个 candidate 做末端小惩罚**
- **而要在 `Apply()` 里更早地改变 family/edge 的资格或竞争格局**

## 当前更合理的前移版原型

所以，下一轮最值得做的原型，不是：

- `ComputeTranslatorLinkedGuardBias()` 这种 candidate 级小惩罚

而是类似下面这种 family/edge 级结构介入：

### 方案 A：family qualification penalty

核心思想：

- 先在每个 `start -> end` family 内做一次 linked-guard 资格汇总
- 如果 family 的“主 exact 候选”命中：
  - `wrong_family_with_path_unconfirmed`
  - 或 `wrong_family_with_path_unconfirmed_dead_tail`
- 那么惩罚的不再只是该 candidate，而是该 family 的竞争资格

具体可以做成：

1. 先计算 family 级 summary：
   - 是否存在 linked-guard 主 exact 候选
   - 是否存在 clean / stronger exact sibling
   - dead-tail 是否出现
2. 再对该 `end_entry` 下整组候选施加 family penalty
   - 而不是只对某一个 candidate 加小罚分

这样作用点会更早：

- 它改变的是这条 family 在图里的整体竞争地位
- 后续 `poet` 接手时，已经看到一个被重新整形过的 graph

### 方案 B：soft edge demotion

如果不想直接惩罚整组 family，也可以做成更保守的 edge 级降权：

- 当 `start -> end` 这条 edge 的 best exact family 命中 linked guard
- 且不存在足够强的 clean exact 支撑
- 就给整个 edge 一个 soft demotion

这比 candidate 末端补罚更早，也更接近：

- `path qualification`

### 为什么这两种都比当前原型更对

因为当前 `Phase 1` 的失败已经说明：

- 仅对命中 `wrong_family_with_path_unconfirmed` 的 candidate 做小负向 bias
- 仍然太像“句尾修修补补”

而 family/edge 资格介入改变的是：

- 哪条路径在 graph 阶段就被视为更可信

这才更接近我们前面离线分析得出的本质：

- 这条信号更像“资格约束”
- 而不是“末端附加特征”

## 与现有 poet penalty 的关系

这一步也顺便澄清了和 `poet` 的分工：

- `poet` 现有的
  - `upstream_path_prior_penalty`
  - `early_unstable_continuation_penalty`
  - `whole_first_word_continuation_penalty`
  - `beam_merge_penalty`
- 更适合继续处理：
  - fallback / OOV / joint risk / single-char tail 这类连续路径信号

而 `linked_guard` 的这条线更适合处理：

- family 内 exact 候选相对关系
- path qualification / family qualification

因此，两者并不冲突，但职责边界应该重新划清：

- `poet` 负责连续风险
- `translator graph rewriter` 负责 family/path 资格

所以当前最稳的工程判断已经可以写成一句话：

- **下一轮真正值得实现的，不是更大的 `upstream_linked_guard_weight`，也不是直接改 `poet`，而是把 linked guard 前移成 `WordGraphRewriter::Apply()` 中的 family/edge qualification 原型。**

### 这轮新增的非重复判断 2：`entry->weight` 的动态部分当前主要来自 table query credibility，而不是 translator 侧 ledger 直接回灌

继续往上游追 `entry->weight` 的来源后，当前可以更精确地区分两层：

  - 而不能直接说成：

### 再对齐 scorer 实现后，`第一站` 的问题已经可以正式写成“prefix 状态失血”

#### 运行时事实

当前已确认：

- `word = 第一站`
- `matched_whole_word = false`
- `used_char_fallback = true`
- `oov_token_count = 1`

#### 这在 scorer 里不只是单步现象

`witset_poet.cc` 当前有一整组 adjustment 项，不只看当前步，还显式依赖 prefix 累计状态：

- `prefix_fallback_hits`
- `prefix_oov_tokens`
- `prefix_whole_word_hits`

其中可以分成两类：

#### 第一类：要求 clean whole-word prefix 才给奖励

- `ComputeCleanFirstWordBridgeBonus(...)`
- `ComputeCleanSingleCharBridgeBonus(...)`
- `ComputeCleanExactContinuationBonus(...)`
- `ComputeValidatedPrefixSuffixBonus(...)`
- `ComputeStableWholeContinuationBonus(...)`

这些项都要求 prefix 侧满足类似条件：

- 有 `whole_word_hits`
- 没有 fallback
- 没有 OOV

#### 第二类：前缀一旦 fallback / OOV，会转入补偿或惩罚分支

- `ComputeEarlyBoundaryBridgeCompensation(...)`
  - 只有在 prefix 已经 fallback + OOV，而当前步是干净单字命中时，才给“补桥”补偿
- `ComputeEarlyUnstableContinuationPenalty(...)`
  - 当前缀已经 fallback + OOV，且当前 continuation 继续不稳时，再追加惩罚
- `ComputePrefixAnchorDeltaDebtPenalty(...)`
- `ComputeWholeFirstWordContinuationPenalty(...)`
  - 都会继续跟踪 prefix anchor 之后新增的 fallback / OOV 账本

### 这对 `第一站是一座...` 的含义

因此，当前 `第一站` 一旦在 source line 建立阶段就落入：

- whole-word miss
- char fallback
- OOV

后面不只是“这一步 LM 过渡差一点”，而是会引发两层后果：

1. 原本属于 clean whole-word prefix 的一整组 bonus 直接拿不到
2. 后续 continuation 一旦继续不稳，更容易进入 fallback / debt / unstable penalty 分支

### 到这里，当前 case 的主问题可以改写成

所以现在对 `第一站是一座古老的小镇`，更准确的工程表述已经不是：

- `yi` 本跳排序坏了

而是：

- **句首正确整块 `第一站` 没有建立 clean whole-word prefix state**
- **这个 prefix 失血状态又被 `witset_poet` scorer 持续传递到后续 continuation 竞争里**

也就是说：

## prefix-state repair v1 结论

在确认 `体验不`、`两旁是` 这类 case 是被 `prefix_state` 提前打成 `family_drifted` 之后，我先做了一版最小 `prefix-state repair`，目标很单一：

- 不是提高所有 request-stage 候选的分数
- 而是让“已有 strong exact 前缀后的单字 exact bridge”不要被过早判 drift

### 实现方式

这版 repair 只做了最小状态修正：

- `PrefixPathState` / `LinkedGuardPrefixState` 新增 `exact_single_char_bridge_count`
- 新增 `CanPreserveTranslatorPrefixCleanliness()`
- 在 `BuildBestPrefixStates()` / `BuildLinkedGuardPrefixStates()` 中：
  - 若当前前缀已经有 `exact_multi_word_count >= 1`
  - 且尚未 drift
  - 且当前候选是单字 exact
  - 则允许保留一次 bridge，不立刻把 `has_inexact_segment` 置为 `true`
- 为避免放水过大，bridge 次数当前只允许 `1` 次

### 验证结果

#### 1. gate reopening 成立

对目标 case 复测后：

- `体验不`
  - 从 `family_drifted` -> `family_soft_clean`
  - `supports_validated_continuation` 从 `false` -> `true`
- `两旁是`
  - 从 `family_drifted` -> `family_soft_clean`
  - `supports_validated_continuation` 从 `false` -> `true`

同时：

- `第一站`
  - 仍是 `family_soft_clean`
- `一直向往着`
  - 仍是 `family_clean`

说明这轮 repair 打中了真实断点，而且没有破坏之前已经 clean 的 prefix。

#### 2. 但总代表集没有新增净收益

在 shared-prefix 21 条代表集上重新跑 `weight = 1.0`：

- `top1_accuracy = 0.619048`
- `top3_accuracy = 0.714286`
- `expected_not_found_count = 4`

与上一轮 `request_stage_on` 完全一致。

这说明：

- **prefix-state repair 已经完成了“重新开 gate”这一步**
- 但 **只开 gate 还不足以改变最终排序**

### 这对后续实现的意义

这轮结果把因果关系进一步拆清了：

1. `prefix-state repair` 是必要条件
- 不修它，`体验不`、`两旁是` 这类 case 连 contract gate 都进不去

2. 但它不是充分条件
- gate 开了以后，内部仍然缺少能区分正确主轴的 next-hop ranking contract

因此下一步最合理的方向不是继续微调这版 repair，而是继续把主力放回：

- `一直向往着 -> 远 / 与 / 于`
- `第一站 -> 是 / 式 / 十 / 事`

这种 source-line next-hop 的主轴区分能力。

更准确地说：

- 这轮 repair 已经证明：
  - 之前的 drift 问题是真实存在的
  - 修 gate 是必要的
- 下一步则应承认：
  - **真正决定新增收益的，不再是 gate 是否打开，而是 gate 内部是否能识别正确 next-hop 主轴**
