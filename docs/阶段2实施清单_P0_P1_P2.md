# 阶段 2 实施清单：P0 / P1 / P2

## 1. 文档目的

这份文档把阶段 2 从“宏观方案”进一步收束成**可执行清单**。

它服务于两个已经写死的前提：

1. `witogram` 必须保持为可独立开源给 Rime 社区使用的一档实现。
2. 一档必须以“持平或超过原版 `octagram` 的准确率”为最主要目标。

若两者在执行过程中出现阶段性冲突，只允许牺牲：

- 物理分拆时机
- 过程中的代码整洁度

不允许牺牲：

- 一档准确率持平/超越原版的目标

---

---

## 2. 阶段 2 的总目标

阶段 2 的总目标不是一次性把全部问题都解完，而是按最小闭环顺序完成三步：

1. **P0：grammar 语义纠偏**
2. **P1：上游 contract 前移**
3. **P2：搜索形态改造**

这三步必须按顺序推进。

原因是：

- 如果不先做 P0，P1 和 P2 都会建立在错误的 grammar 解释语义上。
- 如果不做 P1，P2 会继续承担“先放大候选、后末端补救”的不合理负担。
- 如果不做 P2，即便 P0 和 P1 成立，也未必能稳定超过原版 `octagram`。

---

## 3. 非目标

阶段 2 明确**不做**下面这些事：

1. 不提前做开源/闭源物理分拆。
2. 不新增二档、三档能力。
3. 不回到 `witset_poet` 末端救火 patch。
4. 不为了让某个单句做对而牺牲代表集指标。
5. 不为了漂亮的开源边界而回避当前最需要改的 grammar 语义问题。

---

## 4. 验证资产

阶段 2 统一使用三层验证资产，避免只盯单句：

## 4.1 目标类错例

用于快速判断主问题是否被直接命中。

建议固定至少包含：

1. `第一站是一座古老的小镇`
2. `一直向往着远方`
3. `体验不一样的生活`
4. `两旁是古色古香的建筑`

其中第一句是当前 grammar 语义错位最典型的代表句。

## 4.2 shared-prefix 代表集

用于验证：

- source-line / family ownership
- request-stage admission
- 错误 family 是否仍会借同 prefix 混入

这部分继续沿用当前已建立的 shared-prefix 代表集，不改测试目标。

## 4.3 基线集

用于判断是否真的接近、持平或超过原版。

继续使用现有基线文档和工件：

1. `docs/validation_baseline.md`
2. `docs/benchmark_artifacts/octagram_300_20260516`

阶段 2 的任何结论都必须至少同时满足：

1. 目标类错例方向正确
2. shared-prefix 代表集不恶化
3. 基线集整体不倒退

## 5. P0：grammar 语义纠偏

## 5.1 目标

修正当前最明确的主失配：

- 不能再把当前万象 grammar 中的 `NotFound()` 普遍解释成重 OOV / fallback 坏路径

更准确地说，要把当前 grammar 结果拆成三类：

1. 正证据
2. 中性缺证
3. 真负证据

## 5.2 主要落点

P0 重点改动范围应收敛在：

1. `librime/plugins/witogram/src/witogram.cc`
2. `librime/plugins/witset/src/witset_poet.cc`
3. 未来 `InterpretGrammarEvidence` 对应的内部边界

优先关注：

1. `vocab.Index(word) == NotFound()` 的当前解释语义
2. `used_char_fallback`
3. `oov_token_count`
4. 它们在句级层如何被继续放大成惩罚

## 5.3 建议改动边界

P0 可以做：

1. 将 `NotFound()` 从“重 OOV”语义中拆开
2. 显式引入：
   - `direct_hit`
   - `split_token_supported`
   - `neutral_missing`
   - `true_oov`
3. 将目标类错例中的 `一` 类 token 从系统性误伤里剥出来

P0 不应做：

1. 顺手新增 family/path 奖惩
2. 顺手新增 beam state contract
3. 顺手改候选池扩张策略

## 5.4 成功标准

P0 判定成功至少需要满足：

1. `第一站是 -> 一` 这类路径不再稳定显示为重 OOV / fallback 坏路径
2. graph / snapshot 能解释这种变化来自 grammar 语义纠偏，而不是别的偶然连带效应
3. 目标类错例没有出现“误伤减少了，但错误 family 反而整体泛滥”的明显副作用

## 5.5 止损条件

出现以下任一情况，P0 应立即止损，不进入 P1：

1. 目标类错例改善不明显，且 graph/snapshot 仍显示 `NotFound()` 被原样放大
2. 代表集大面积恶化，说明“中性缺证”被放得过宽
3. 修改开始扩散到上游 contract 或搜索形态，边界失控

---

## 6. P1：上游 contract 前移

## 6.1 目标

在 P0 语义纠偏完成后，进一步让系统更接近原版 `octagram` 的有效结构：

- 更早保住正确 family
- 更早压掉错误 family

## 6.2 主要落点

P1 重点改动范围应收敛在：

1. `librime/plugins/witset/src/witset_translator.cc`
2. 未来 `CredibilityLedgerBuilder`
3. 未来 `WordGraphRewriter`
4. `BuildRequestStagePrefixStates()` 及相关 request-stage contract

## 6.3 应优先建立的 contract

阶段 2 的 P1 不再做粗 continuation bonus，而是优先补齐：

1. `source-line ownership`
2. `family continuity`
3. `continuation legality`
4. `request-stage admission`

## 6.4 建议改动边界

P1 可以做：

1. 扩展 `CredibilityLedger`
2. 强化 `WordGraphRewriter`
3. 按 family/source-line 定义 request-stage state
4. 用结构化准入替代表面 text 级别的粗奖励

P1 不应做：

1. 再回到 `clean_first_word_bridge` 这类 surface bonus
2. 仅通过“再加一个 weight”试图解决 family/path 问题
3. 把本应由 P2 处理的搜索形态问题提前塞回上游

## 6.5 成功标准

P1 判定成功至少需要满足：

1. shared-prefix 代表集里，正确 family 更早进入 eligible 状态
2. 错误 family 不再轻易借同 prefix 混入
3. 目标类错例在 graph 读数上已出现更干净的 source-line / family 读数
4. 基线集整体开始逼近原版，而不是只改善个别句子

## 6.6 止损条件

出现以下任一情况，P1 应止损并复盘：

1. graph 中 family/path 读数变化很多，但 baseline 几乎静默
2. 正确 family 和错误 family 被一起抬高，说明 contract 仍过宽
3. 为了让 contract 生效，又回到了 continuation 奖惩的旧实验形态

## 7. P2：搜索形态改造 + 系统偏差消除

### 7.0 P1 收口结论（2026-05-27）

P1 预验证阶段已覆盖 path_confirmation / family-tail / request-stage ownership / path-debt 子线。
核心发现：

1. **SelectTopLines 是 case1 的真正上游断点**：正确 family 的 `一直向往着远`（weight=-227）被错误 family 的 `一直想王者`（weight=-148）以约 78.8 分挤出 top_candidate。
2. **前缀 gap 来源分散**：Base 积累（91%）+ LmScaled（95%）双重主导，不存在单一可修 P1 信号。
3. **path-debt 无区分力**：两 family 在关键分叉步骤上的债务 profile 完全一致。
4. **P1 已无新的未重复入口**，应进入 P2。

### 7.1 目标（更新）

原 P2 目标（搜索形态改造）保留，但根据 P1 证据新增一个同等优先级的目标：

**家族多样性保持**：在 SelectTopLines 等剪枝点，不纯按 score 截断，而是保证每个主要 family 至少有一条代表进入候选。这不是"放宽 beam"——而是给正确的但暂时分值落后的 family 一个最小的存活空间。

原目标不变：

- 少放大
- 早准入
- 保持正确状态

### 7.2 主要落点

P2 重点改动范围应收敛在：

1. `librime/plugins/witset/src/witset_poet.cc`（SelectTopLines, CompressLinePoolByState, PruneLinePool）
2. 未来 `RunWitogramPoet`
3. 与状态压缩、admission、近似 beam-Viterbi 相关的结构

### 7.3 优先尝试方向（更新）

P2 优先验证（按优先级排列）：

1. **家族感知 SelectTopLines**：在现有 top_k beam 选择的基础上，额外保留每个主要 family 的最佳代表行。家族身份可从 `source_text` 的近似前缀或 `family_identity` 推导。
2. 状态化 admission
3. 近似 beam-Viterbi
4. best-only admission 前移
5. 控制状态分裂与重复扩张

P2 的目标是让句级层更多地做：

1. 长句一致性
2. 多词块组合偏好
3. 全局结构判别
4. 家族多样性保持

而不是继续承担：

1. grammar 语义纠偏
2. 上游 family/path 主救火

## 7.4 成功标准

P2 判定成功至少需要满足：

1. 固定 baseline 上，一档整体达到或超过当前 `octagram`
2. 若声称“超越成立”，需在固定 baseline 上可重复复现
3. 提升能够被搜索形态变化解释，而不是末端 patch 偶然碰对
4. 候选数、状态扩张率或 wall time 至少有一项出现可解释的结构改善

## 7.5 止损条件

出现以下任一情况，P2 应止损：

1. 新改动实质上又变成末端救火 patch
2. 状态维度急剧膨胀，但准确率没有相应收益
3. 单句改善明显，但代表集和 baseline 不跟

## 7A. P2 补充方向：系统偏差消除

以下方向来自 P1 预验证证据，可与 P2 并行推进或作为前置验证。

### 7A.1 步骤 1 根因：`一直向` 词典覆盖

**证据**：在 `yizhixiang` 步骤，正确 family `一直向` 从未进入 beam top 20。
**待验证**：`一直向` 是否在词典中？
**成本**：极低（一次词典查询）。

### 7A.2 LM 分值审计：`向往` vs `想往`

**证据**：步骤 2 的 22.89 LM raw gap 是 case1 最大单一贡献源。
**待验证**：差距是真实语料频率差异还是 tokenization 偏差？
**成本**：中等（KenLM query / 模型审计）。

### 7A.3 LmScaled 缩放不对称调查

**证据**：正确 family LmScaled/LmRaw=0.841 vs 错误=0.742（步骤 3），0.910 vs 0.847（步骤 4）。
**待验证**：追查 `prefix_char_fallback_lm_scale` 及相关 LM 缩放逻辑。
**成本**：中等（代码审计 + 参数实验）。

## 8. 阶段 2 的正式 Gate

## 8.1 进入 P1 的 Gate

必须同时满足：

1. P0 已完成
2. 目标类错例不再被 `NotFound()` 系统性误伤
3. 没有明显放大错误 family 的副作用

## 8.1.1 当前执行结论（2026-05-25）

当前状态需要和正式 gate 分开表述：

1. **正式 gate 口径不变**
2. **工程执行上，建议继续做受控的 P1 预验证**

原因是：

1. `P0` 第一刀已经证明 grammar 语义纠偏方向是对的：
   - `第一站 -> 是` 已不再表现为被 `fallback/OOV` 误罚的脏路径
   - `used_char_fallback = false`
   - `lm_oov_token_count = 0`
2. 但 `P0` 仍未通过正式验收：
   - 主竞争盘面还没有回到“以 `第一站是` 为主轴的干净 request-line”
   - 错误 family 仍会在后续竞争中漂到 `第一站是以 / 地一站式 / 第一展示 / 第一战士` 等路径
3. 当前剩余 blocker 已经不再像纯 `P0` 问题：
   - 更像是 `RewriteWordGraph`
   - `request-stage state ownership`
   - `source-line / family continuity`
   - `beam/source_pool` 选源阶段
   的上游 contract 问题

因此，当前更准确的推进口径应是：

1. **不把 `P0` 宣告为已通过**
2. **不修改 8.1 的正式 gate**
3. **允许继续做 P1 侧的预验证/原型/探针，用来解释并解决 `P0` 后残余的 family drift**

这里的“继续 P1”只允许指：

1. 补 `source-line ownership`
2. 补 `family continuity`
3. 补 `continuation legality`
4. 补 `request-stage admission`
5. 直接查清 residual drift 发生在：
   - `RewriteWordGraph`
   - `BuildRequestStagePrefixStates()`
   - 还是 `beam/source_pool` 选源

这里的“继续 P1”明确**不允许**退回成：

1. 再打一轮 `P0` 同构语义微调
2. 再调 `oov_penalty / char_fallback_penalty`
3. 再回到 `witset_poet` 末端 bonus/penalty
4. 用新的 surface bonus 冒充 family/path contract

建议把当前状态记为：

- `P0`：核心方向成立，正式 gate 未过
- `P1`：允许开始受控预验证，但不能宣称“已正式进入 P1 完整推进”

## 8.2 进入 P2 的 Gate

必须同时满足：

1. P1 已完成
2. shared-prefix 代表集出现稳定正信号
3. graph / snapshot 能解释改善来自 family/path contract

## 8.3 进入阶段 3 的 Gate

必须同时满足：

1. 一档整体至少持平 `octagram`
2. 对“超过 `octagram`”已有稳定信号，而不是偶发领先
3. 当前一档逻辑已经能按未来 `witogram_core` 边界清晰归类
4. 没有把闭源概念混入未来开源接口

---

## 9. 推荐执行顺序

建议阶段 2 严格按下面顺序推进：

1. 先做 P0
2. P0 通过后再做 P1
3. P1 通过后再做 P2
4. P2 至少持平后，再进入阶段 3 的正式分拆准备

这份顺序不允许颠倒。

当前执行注记（2026-05-25）：

1. 顺序本身不改，正式 gate 仍按 `P0 -> P1 -> P2` 执行
2. 但在 `P0` 已证明“方向成立但 gate 未过”的情况下，可以先做**受控的 P1 预验证**
3. 这类预验证只用于解释和解决 `P0` 后残余的 family drift，不等于正式跳过 `P0`
4. 只有当 8.1 的条件被真正满足后，才能把项目状态记为“P0 通过、正式进入 P1”

---

## 10. 一句话版

阶段 2 不是“继续试更多 patch”，而是按 `P0 语义纠偏 -> P1 上游 contract -> P2 搜索形态改造` 的顺序，先把当前万象模型与当前实现的错位修正，再把一档推到至少持平 `octagram`，然后才进入正式的开源/闭源物理分拆。
