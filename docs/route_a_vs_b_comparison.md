# Witogram 路线 A / B 对比与可行性报告

## 1. 文档目的

本文档用于回答三个问题：

1. `witogram` 后续演进为什么需要在路线 A 与路线 B 之间做选择；
2. 两条路线分别意味着什么、优缺点是什么；
3. 为什么当前建议选择路线 B，以及路线 B 是否真正可行。

本文档是 [route_b_implementation_plan.md](./route_b_implementation_plan.md) 的补充说明，重点放在“路线比较”和“可行性评估”。

---

## 2. 当前背景

`witogram` 当前已经具备了一些明确成立的工程能力：

- `KenLM` 模型加载
- `mmap` 驻留内存优势
- UTF-8 查询链路修复
- 线程安全的模型缓存
- 运行时去掉旧 `Darts::DoubleArray` 依赖

但同时也存在两个核心问题：

1. 当前 `.gram -> .arpa -> .klm` 转换链路仍然是兼容性优先的过渡实现；
2. 当前 `witogram` 与 `witset_poet` 的评分融合还不是一个已经完成校准的句级评分体系。

这意味着：

- `witogram` 已经不是旧 `octagram` 的简单源码替换；
- 但它也还没有真正完成“上位替代”所需要的排序质量证明。

后续必须明确演进方向。

---

## 3. 路线 A 是什么

## 3.1 定义

路线 A 的核心思路是：

- 尽量保留 Rime 原生 `grammar` 契约；
- 将 `witogram` 继续实现为一个兼容 `Grammar::Query()` 的插件；
- 通过优化 `Query()` 返回值、调整转换脚本、微调权重，逐步逼近原 `octagram` 甚至超越它。

换句话说，路线 A 是：

- **以兼容为中心的渐进式改造**

## 3.2 路线 A 的优点

1. **改动范围小**
   - 不需要大幅重写 `witset_poet` 的评分结构
   - 对现有 Rime 接口侵入较低
2. **接入路径简单**
   - 继续沿用 `grammar/language`、`grammar/weight`
   - 更接近原 `octagram` 的使用方式
3. **短期试错成本低**
   - 可以快速验证某些转换脚本或 `Query()` 层面的改动

## 3.3 路线 A 的缺点

1. **上限低**
   - Rime 原生 `grammar` 契约本质上是一个“附加打分项”，不适合多特征句级融合
2. **可解释性差**
   - 很难把最终分数拆解成多个稳定特征
3. **容易陷入长期调权重**
   - `entry->weight`、`grammar.weight`、转换后的 LM 分数三者之间很容易互相污染
4. **很难支撑 README 中更大的目标**
   - 比如“更科学的评分体系”“真正的上位替代”

## 3.4 路线 A 更适合什么目标

路线 A 更适合：

- 希望尽快得到一个“能用、兼容、工程风险低”的版本；
- 接受它只是一个相对保守的替代方案；
- 不强求在评分理念和验证体系上做根本升级。

---

## 4. 路线 B 是什么

## 4.1 定义

路线 B 的核心思路是：

- 不再把 `witogram` 只当成 Rime 原生 `grammar` 插件；
- 由 `witset` 自己的 `Poet` 接管句级评分逻辑；
- 将 `witogram` 收束为一个“语言模型特征提供器”；
- 在 `witset_poet` 中显式做句级特征融合、调试输出、验证和回归。

换句话说，路线 B 是：

- **以句级评分系统重构为中心的升级路线**

## 4.2 路线 B 的优点

1. **上限高**
   - 可以真正做句级特征融合
2. **可解释**
   - 每个候选的分数可以拆开看
3. **可验证**
   - 可建立标准化离线评测和回归集
4. **适合长期演化**
   - 后续可自然引入边界特征、OOV 惩罚、用户词典加成，甚至更高层级的语义特征
5. **更符合“上位替代”的目标**
   - 不只是兼容旧接口，而是重建一套更强的排序体系

## 4.3 路线 B 的代价

1. **改动范围更大**
   - `witset_poet` 必须重构
2. **验证工作量更大**
   - 必须建立自动化评测，而不能靠人工试句
3. **短期内更复杂**
   - 需要先搭基础设施，短时间内未必立刻见效
4. **需要关注与 `OutwitSettingsServer` 的联动边界**
   - 不能为了改造 `witset` 破坏本地纠错、PPL、重排序等既有能力

## 4.4 路线 B 更适合什么目标

路线 B 更适合：

- 目标不是“能跑”，而是“做到极致”；
- 希望 README 里的优势最终真正成立；
- 愿意为更高上限付出更多工程和验证成本。

---

## 5. 路线 A / B 对比

| 维度 | 路线 A | 路线 B |
| ---- | ---- | ---- |
| 核心目标 | 保持兼容、局部优化 | 重建句级评分体系 |
| 改动范围 | 小到中 | 中到大 |
| 上限 | 较低 | 较高 |
| 可解释性 | 弱 | 强 |
| 自动化验证价值 | 中 | 高 |
| 对 README 的支撑能力 | 有限 | 强 |
| 短期落地速度 | 快 | 中 |
| 长期可维护性 | 一般 | 更好 |
| 对 `witset` / SettingsServer 联动的要求 | 较低 | 更高 |

简化理解：

- 路线 A 更像“把现有系统打磨好”
- 路线 B 更像“把现有系统升级成新的架构层”

---

## 6. 为什么当前选择路线 B

当前建议选择路线 B，原因不是“路线 A 一定做不成”，而是：

### 6.1 路线 A 解决不了根问题

当前最大问题已经不是某一个权重值，而是：

- 模型转换语义不够稳定
- 分数融合契约不清晰
- 排序错误难以解释

这些问题如果继续塞在旧的 `grammar` 契约里，只会变成长期“修一处、漏一处”的状态。

### 6.2 路线 B 更符合现有演进现实

`witogram` 已经做了很多并非“简单兼容替换”能解释的事情：

- `KenLM`
- `mmap`
- UTF-8 修复
- 去掉运行时 Darts

这说明项目已经客观上走到了“新架构基础”阶段。

既然如此，与其继续假装它只是一个轻量 grammar 插件，不如承认并利用这个事实，让评分系统也升级。

### 6.3 路线 B 更能支撑对外叙事

如果未来还想保留这些目标：

- 更科学的评分体系
- 更强的长句排序能力
- 真正的上位替代

那么必须有一套：

- 可解释
- 可验证
- 可演进

的评分框架。路线 B 更接近这个方向。

---

## 7. 路线 B 的可行性报告

## 7.1 可行性结论

总体判断：

- **路线 B 可行**
- **且值得投入**

但需要明确，它不是“一个小 patch”，而是一个有阶段性的架构升级任务。

## 7.2 为什么说它可行

### 原因 1：关键控制点都在当前仓库内

路线 B 最关键的两个改造点都在我们可控范围内：

- `witogram`
- `witset_poet`

这意味着不需要去修改大量 Rime 核心代码，主要是围绕插件自己的能力升级。

### 原因 2：已有工程基础已经足够

当前并不是从零开始：

- 模型加载已有
- UTF-8 链路已有
- `mmap` 已有
- 文档基线已开始建立

路线 B 不需要从头发明一切，而是在此基础上重建评分契约。

### 原因 3：验证可以高度自动化

我们已经明确了样例来源：

- [test-sentences.txt](file:///c:/Code/outwit/outwit-windows/librime/plugins/witset/docs/test-sentences.txt)

也已经建立了验证基线文档：

- [validation_baseline.md](./validation_baseline.md)

这使得路线 B 不会沦为纯主观开发。

## 7.3 路线 B 的主要风险

1. **评分重构时误伤 `witset` 与 `OutwitSettingsServer` 联动**
2. **转换链路继续失真，导致句级契约重构后仍然受限**
3. **早期引入太多特征，使定位问题变难**
4. **性能变差**

## 7.4 风险可控吗

整体可控，但必须按阶段推进。

最关键的控制原则是：

1. 先做分项打分与日志，不立刻大改所有逻辑；
2. 每次只增加少量特征；
3. 先建立回归集，再做结构性重构；
4. 改 `witset` 时必须同步关注它和 `OutwitSettingsServer` 的交互链路。

---

## 8. 路线 B 对 `witset` / `OutwitSettingsServer` 的影响

这一点必须单独强调。

`witset` 不是一个孤立插件，它还联动：

- 本地纠错
- PPL 请求
- 候选聚类
- `OutwitSettingsServer` 的后端打分与重排序能力

因此，路线 B 的原则不是“把所有评分都推翻重来”，而是：

1. 先明确哪些分数属于 `witogram` / `witset_poet` 本地句级排序；
2. 哪些逻辑属于 `OutwitSettingsServer` 的后续能力；
3. 改造时不得破坏：
   - 候选生成链路
   - PPL 请求时机
   - 重排序输入输出结构

简单说：

- 路线 B 是“升级本地句级评分基础”
- 不是“删除或削弱 SettingsServer 的后续能力”

---

## 9. 预计工作量

以下为偏现实的估算。

### 第一阶段：评分拆解与验证基础设施

工作内容：

- 拆出显式分项分数
- 输出可解析日志
- 接入基线样例
- 建立离线回归脚本

预计工作量：

- 4 到 7 天

### 第二阶段：重做转换链路

工作内容：

- 重构 `dump_to_arpa`
- 重新转换模型
- 跑回归对比

预计工作量：

- 5 到 10 天

### 第三阶段：训练自己的标准 KenLM

工作内容：

- 语料准备
- 训练字级或字词混合模型
- 接入并对比

预计工作量：

- 若语料现成：5 到 8 天
- 若语料需系统清洗：1 到 3 周

---

## 10. 推荐结论

综合比较后，建议如下：

1. 选择路线 B；
2. 但不要一次性大爆炸式改造；
3. 先推进第一阶段：
   - 分项打分
   - 调试输出
   - 自动化验证
   - 明确 `witset` 与 `OutwitSettingsServer` 联动边界
4. 在验证基础设施稳定后，再推进转换链路和模型层升级。

换句话说：

- **路线 B 是正确方向**
- **但必须以验证和边界控制为前提**

只有这样，`witogram` 才有可能从“工程上更新的插件”真正成长为“排序质量上也站得住的上位方案”。
